# XB22Q5 controller CROM trace

This is an offline trace of the ET-3850 XB22Q5 controller image. It does not establish that the live printer accepts a modified image. No firmware image has been sent to the printer.

## Image and address mapping

The RCX with SHA-256 `103c9514e57f143f2619abcd280bd4d0926abf5370e03d28753a334ae02cd675` contains a CROM region at RCX offset `0x167112`, inside its first IPL. The [hash-checked extractor](../scripts/extract_controller_crom.py) uses the public [abrasive/epson-reversing decoder](https://github.com/abrasive/epson-reversing) to produce segment 0, 5,686,304 bytes with SHA-256 `7bdc1c0562adda78bb541cbadac1ac104367c0b839262ea1f51d38e07a54e416`, and segment 1, 3,036 bytes with SHA-256 `5c6af9a703999265215faeb814cb1e06cf38bbcfef8d78b703bcd031962caeb9`. The C and Python decoders gave identical segment hashes. The [all-region inventory](../scripts/inventory_crom_regions.py) found five CROM regions and eight segments; this segment alone contained the exact `GetRequestID` string among the selected probes.

**Address correction:** Segment 0 loads at **`0x4566ff74`**. The original Ghidra project was imported at provisional base `0x45670000`, 0x8c too high. All Ghidra addresses quoted below are provisional; subtract `0x8c` for runtime addresses. Embedded absolute pointers are already runtime addresses. This correction resolves the request and event tables and retracts the former [low-address-write lead](controller-event-table-memory-safety.md).

## Linux POST to ROM selection

The [isolated Linux HTTP rehost](application-rehost.md) captured `EpsonLocalReq:GetRequestID` with `Method:POST`, the full `URI:/DOWN/FIRMWAREUPDATE/ROM1`, and `IFIndex:1` on the D4 controller-facing channel. The controller's `FUN_4590ea54` tests the `EpsonLocalReq:` prefix, then scans 38 name/callback pairs. The [hash-checked table inspector](../scripts/inspect_controller_request_table.py) finds `GetRequestID` at runtime string address `0x45bce165` and its callback at runtime `0x459126b4` (Ghidra `0x45912740`). Thus the first-stage Linux message has a matching controller parser in the decoded image. Whether that message was accepted on the physical printer is still unmeasured.

The callback parses `Method:` and `URI:` records. Its POST branch compares the path against a string pointer at `0x459133f8` in the provisional Ghidra image; that literal resolves to runtime string `/DOWN/FIRMWAREUPDATE/` at `0x45ae58c3`. It queues event group `0x76`, subcommand `8`, with the path suffix and a reply callback. The corrected group `0x76` jump table sends subcommand `8` to runtime `0x45809a2c` (Ghidra `0x45809ab8`), which calls the ROM selector at Ghidra `0x458089a4`. The [dispatch inspector](../scripts/inspect_update_event_dispatch.py) and [isolated ARM dispatch run](../scripts/emulate_update_event_dispatch.py) reproduce the correct table target.

The separate controller `/FIRMWAREUPDATE` prefix callback queues event `0x76/6`, which the corrected table routes to Ghidra `0x45808b2c`. This preparation function moves update state `0` to `1`, and can move state `1` to `5` after readiness checks. A new ROM request requires state `5`. One live GET-only control returned 200 and left SNMP uptime increasing for 30 seconds; a GET followed by an invalid 20-byte POST returned 500 and coincided with a network/SNMP uptime reset. This does not establish the exact live state. Details are in the [network route trace](network-update-route-trace.md).

The ROM selector checks state `5`, compares the suffix to `ROM1` or `ROM2`, allocates a request ID, and queues group `5`, subcommand `3`, for branch IDs `0xb` or `0xc`. The corrected group `5` handler calls runtime `0x457e8718`; the ROM1 branch `0xb` selects callback IDs `0x11` and `0x12` through runtime `0x457e861c`. A [hash-checked update-chain inspector](../scripts/inspect_controller_update_chain.py) reproduces these pointers and handlers.

The parser stores runtime reply callback `0x459125b4` (Ghidra `0x45912640`) in the ROM event. This callback maps selector result `-1` to HTTP 500, `0` to 503, and a nonzero result to 200; it includes `ChID:1` and the returned request ID. The controller allocator at Ghidra `0x45808980` returns the previous counter and increments it; its live initial value is unknown. The [offline Linux rehost](application-rehost.md) now completes a body transfer with **fabricated** `RequestID:1`, `ChID:1`, and a matching D4 frame ID. This matches the controller reply's nonzero-ID and channel shape, but it does not capture the physical printer's reply. A standalone live POST with a 20-byte invalid marker returned HTTP 500 without an SNMP uptime reset; a preparation GET followed by the same POST coincided with an uptime reset. Neither response locates the signature gate.

The corrected group `0x77` dispatch table has six entries. Subcommand `3` reaches the package source event at runtime `0x457775ac`, and subcommand `5` reaches the package receiver at `0x457773fc`. The source event saves its input callback and context, then reads two-byte chunks until an end marker; the end-marker branch queues subcommand `5`. In receiver modes `0xb` and `0x11`, that subcommand calls the three-record signed reader at runtime `0x45778378`. The [update-chain inspector](../scripts/inspect_controller_update_chain.py) checks the event table and ARM branch targets.

A fresh Ghidra import at the corrected `0x4566ff74` load base showed that the group-`5` dispatcher indexes RAM table `0x43eae878`, dereferences each entry as a six-word callback object, then calls its method at offset `+0x10`. The first IPL startup copy descriptor at raw offset `0x56298` maps source `0x57004` to RAM `0x43e90000` for `0x4c844` bytes. Applying that mapping recovers all 37 table entries: ID `0x11` points to CROM object `0x45ada4ac`, whose `+0x10` method is `0x457dbe3c`; ID `0x12` points to object `0x45ada4c4`, whose `+0x10` method is the group-`0x77/3` sender `0x45776db8`. The sender queues the source event described above. The inspector validates the IPL hash, copy descriptor, table stride, and both methods when supplied `--ipl0-code`.

For ROM1 mode `0xb`, callback ID `0x11` prepares direct read function `0x457db89c` with a fixed context value. The adjacent-callback dispatcher passes that function to ID `0x12`, and the group-`0x77/3` source event uses it to read the package. At `0x457db89c`, the read function calls `0x4589ccf4` with channel `1`, a request ID read from controller record `0x1132`, the destination buffer, and the requested length. This is the controller-side D4 channel read matching the Linux rehost's channel-1 body send. The source end marker queues group `0x77/5`, which reaches the signed reader. This is a static end-to-end path through the extracted code; the isolated Linux mock still fabricates its controller replies, and no live image acceptance is established.

The only `DOWNCONTENT` literal found in this CROM segment occurs inside `EpsonLocalReq:CancelDOWNCONTENT`. Its caller builds a cancel request with `ChID`; it is not the body receiver. Other `RequestID` and `ChID` strings nearby belong to generic local-request framing and replies, so string proximity does not connect the HTTP body to the package reader.

The separate four-byte-prefix table at runtime `0x45ae9e20` has an exact `/FIRMWAREUPDATE` entry and callback. The `EpsonLocalReq:` command table starts at `0x45ae9e48`; the HTTP-response table starts at `0x45ae9f78`. They were previously mistaken for one misaligned table. The [request-table checker](../scripts/inspect_controller_request_table.py) prints all three. One of the 38 command-name pointers is outside this CROM segment, so the whole process still cannot be emulated solely from this segment.

## Controller signed package and trusted key

The controller has a separate `EPSONSIGNXB20d` package reader. Its parser at Ghidra `0x45778e40` copies a 64-byte P-256 public key from running-IPL RAM `0x4fb26800` and the package's 64-byte signature into state. The first IPL's startup descriptor at raw offset `0x5628c` copies 4096 bytes from its own offset `0x13f000` to that RAM address. The copied first 64 bytes match the original RCX key. The [key-source checker](../scripts/inspect_controller_signature_gate.py) reproduces these constants. A replacement public key inside an incoming image does not change the key already loaded from the running IPL.

The reader at Ghidra `0x45778404` processes three IPL records. Its streaming routine hashes payload chunks and invokes the P-256 decision only when the unsigned declared byte count reaches zero. An [isolated ARM run](controller-signature-length-bypass.md) showed that increasing the declared byte count by one leaves one byte pending and allows this reader to return success without ECDSA. The package's original signature still fails against the current IPL key. An earlier IPL mode-2 gate can reject a positive byte count; the live mode and ordering are unknown. The ROM1-to-reader path is now mapped statically, while live network acceptance and any preceding verifier remain unproved.

The reader's header parser also has a separately [reproduced out-of-range index write](controller-package-index-overflow.md). Its immediate type gate rejects that index after the write, and the live input route is unknown.

## Other controller paths

The `SetupData:` producer at Ghidra `0x4589b0fc` is called after a 32-character base64 gate at `0x4591465c`. The traced direct producer places an `IPPRes:` prefix in the supplied bytes, which fails the gate. The [corrected-load ARM gate run](../scripts/emulate_setup_gate.py) rejects that prefix and 31 base64 characters, while 32 base64 characters reach the request call. The group `0x0b` event entries `0x41` and `0x42` are valid branches after the load correction; the former claim that they loop back was an address-mapping error. The direct `SetupData:` producer still does not demonstrate a LAN setup-data route.

An incoming `WriteSetup` command is present in the 38-entry request table. Its callback at Ghidra `0x4591130c` copies data into controller state, but the producer, authorization, and relationship to Linux's [setup restore parser](setup-restore-parser.md) remain unproved. The image also has `ReadSetup`, `CancelDOWNCONTENT`, and a `fl:` command that can queue group `0x8d` events. Those names alone do not establish a safe update or key-changing route.
