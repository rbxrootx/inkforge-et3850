# ET-3850 network update route trace

The XB22Q5 `nwsoc` image contains a six-entry HTTP route table for firmware update paths. [`inspect_network_update_routes.py`](../scripts/inspect_network_update_routes.py) reproduces the table from a separately extracted `nwsoc` binary. The table has paired port 80 and port 443 entries:

| Method and path | Port 80 callback | Port 443 callback |
| --- | --- | --- |
| `GET /FIRMWAREUPDATE` | `0x15593c` | `0x155b98` |
| `GET /FIRMWAREUPDATE/ADMINCHECK` | `0x153b44` | `0x15398c` |
| `POST /DOWN/FIRMWAREUPDATE` | `0x1553b0` | `0x1555e8` |

The table establishes that this firmware was built with POST callbacks for the `/DOWN/FIRMWAREUPDATE` prefix. It does **not** show that `/DOWN/FIRMWAREUPDATE/ROM1` will accept an RCX in normal mode. The earlier live checks used HEAD on other routes and GET on these uppercase routes; no POST body was sent.

Decompilation shows that the port 443 GET and POST callbacks call `0x1534fc` when a global protection flag equals 1. That routine reads `PS_ADMIN_PASSWORD` and parses an HTTP `Authorization: Basic` header; failed authentication produces HTTP 401. When that flag equals 1, the port 80 GET and POST callbacks return HTTP 403 instead of asking for Basic credentials. This looks like a deliberate policy split, not an authentication bypass. The observed first unauthenticated port 80 GET of `/FIRMWAREUPDATE` returned 200; later GETs returned 500 while the printer remained usable. The flag's value during that live probe was not measured, and no sustained denial of service was shown.

Both POST callbacks call `0x170440` before choosing `0x155180` or `0x17111c`. The former enters the common HTTP parser at `0x154708`. The parsed request reaches dispatcher `0x1543D0`. Its cases `5`, `6`, and `7` call `0x0F8EBC`; cases `1`, `2`, and `0x0C` call `0x115574` and then `0x0F5748`. The latter helper builds an internal `URI:` message from the request path (`0x0EE4C8`) and passes it to a configured transport channel (`0x42479C`, then `0x421F4C`). The response path reads from that channel (`0x424624`) and parses an HTTP-like response in `0x0F5014`. This is stronger evidence of an internal relay than of a direct Linux file write.

The `0x170440` branch is now identified as the `SSL_TLS_AUTO_REDIRECT_HTTPS` check. It reads that setting and a connection class; when redirect is selected, `0x17111c` builds a `307 Temporary Redirect` with an `https://` `Location`. It is **not** a second firmware upload parser. The earlier description of it as an unresolved alternate route selector was too broad.

The relay's send side can be followed one layer farther: `0x0F5748` passes the framed message to `0x42479C`, which calls `0x421F4C`. That routine writes the D4/EPIC channel through `0x4740D8`; the latter issues ioctl `0xC018FE02`. The update request therefore crosses the Linux-to-controller IPC boundary. The corrected [controller CROM trace](controller-crom-trace.md) identifies a matching first-stage `GetRequestID` handler and ROM selector. The body receiver and firmware authentication decision remain unidentified; this does not show modified-image acceptance.

The `0x0F8EBC` branch handles a two-stage internal exchange. It first reads an internal response with `0x0F1D4C`. When that status is `200`, its request-type cases `1` and `3` send body buffers through `0x0F867C` and then read a final response with `0x0F5014`. Cases `0` and `2` read the response without calling the body sender. The common HTTP parser initializes that request-type field to `0` and changes it to `1` for selected callback IDs `10`, `17`, and `19`; the firmware POST callback passes ID `7`. This static path suggests that the ordinary ID `7` callback does not forward POST body bytes through that function. Other callbacks, update-preparation state, and runtime changes still need tracing.

A broader [HTTP route-table scan](../scripts/inventory_http_route_table.py) also finds paired `POST /DOWN/` records, distinct from `POST /DOWN/FIRMWAREUPDATE`. Their callback at `0x1571f8` calls the common parser with ID `10`. The [generic body-stream trace](generic-down-stream.md) now follows ID `10` through its own dispatcher case to a conditional D4 chunk sender. The route matcher's precedence for overlapping `/DOWN/` and `/DOWN/FIRMWAREUPDATE` prefixes, the controller's interpretation of any body, and acceptance of a modified RCX are still unproved. No generic `/DOWN/` POST was sent to the printer.

The relay serializer at `0x0E7C00` confirms its request text uses `URI:%s`, an escape separator, and `Method:%s`. Method constants include `GET`, `POST`, `PUT`, and `DELETE`. This verifies that these functions package a request for the internal peer; it does not identify the peer's firmware validation logic.

The HTTP service setup function at `0x16DE88` installs the transport callback at `0x156A3C` through `0x11634C` and a second callback at `0x1528E8` through `0x1162F0`. The former forwards HTTP headers and body chunks through the common channel routines; the latter handles the paired stream response. Its caller at `0x16FC18` reads `SCN_AIRSCAN_ENABLE` and sets `WEBAPP_CURRENT_ACTIVATION` after successful setup. That worker is launched by callback `0x16DAB4` only after two readiness checks and an event whose first byte is `1`. This is WebApp service activation, not proof of a firmware-only update mode. A POST route entry alone is therefore insufficient to establish a live upload path; the route's service activation and controller interpretation still matter.

The same `0x16DE88` function loops over 57 initialized route records of stride `0xb8`, starting at virtual address `0x6B1CFC`. It compares each record's path at offset `+0x14` against a fixed selection and calls route-registration function `0x128DD8` for **matching** records. The [hash-checked operand decoder](../scripts/inspect_http_route_activation.py) confirms that this table contains both generic `/DOWN/` POST records and both specific `/DOWN/FIRMWAREUPDATE` POST records. The selection includes `/FIRMWAREUPDATE`, `/FIRMWAREUPDATE/ADMINCHECK`, and generic `/DOWN/`; it does **not** include `/DOWN/FIRMWAREUPDATE`. The separate function at `0x16F51C` uses the opposite predicate: it calls `0x128DD8` for paths **not matching** its list, which again contains generic `/DOWN/` but not the specific firmware path. Its caller at `0x16F828` checks `SSDP_ENABLE_DISABLE` before invoking it. Thus these flows select opposite sides of the generic-versus-specific split in the inspected image. Registration `0x128DD8` can reach socket setup through `0x125B04`, `0x145644`, and `0x0A72FC`. This narrows how the two paths are activated, but does not establish which flow was active during the live empty POST or prove device acceptance of any body.

The [isolated QEMU WebApp run](application-rehost.md) now confirms a narrower dynamic fact: after shimming missing startup state, this service opened TCP/80 and TCP/443, executed `0x128DD8`, and returned 403 for `GET /FIRMWAREUPDATE`. Two empty POSTs to generic and specific update paths both received an invalid `HTTP/1.1 0 Unknown error` from the incompletely mocked internal peer. A filtered instruction trace resolved the callback in this emulated flow: both POSTs entered generic `0x1571F8`; neither specific callback was reached. This cannot prove which flow was active on the physical printer during its earlier empty POST, establish upload acceptance, or establish a vulnerability.

The mock's D4 send log shows that each generic callback first sends `EpsonLocalReq:GetRequestID` with `Method:POST`, the **full** original `URI:`, and `IFIndex:1`. The longer `/DOWN/FIRMWAREUPDATE/ROM1` URI reaches this internal request intact. The current mock does not implement `GetRequestID`, so no valid controller response, body-stream approval, or signature decision was observed.

An optional offline mock response of invented `HR:200`, `RequestID:0`, and `ChID:1` advanced the empty POSTs into `EPSON-NW-DOWNCONTENT1`; the next D4 command failed and HTTP returned 500. This supports a two-stage Linux-to-controller flow. It is not evidence of a real printer accepting those values or any firmware body.

Using that same synthetic reply, a 19-byte test body sent to the longer URI appeared byte-for-byte in the emulator's EPIDC send log after a D4 length header. This confirms that the **generic handler** can relay body bytes through the Linux IPC layer in this activation flow. The mock's later D4 send failed, and the physical printer received no test body. The real controller's authorization, RCX format check, and signature decision remain unknown.

The trace identifies the D4 controller-facing IPC boundary. Correcting the controller CROM load base to `0x4566ff74` then resolves the `EpsonLocalReq:GetRequestID` command table, its `Method:`/`URI:` parser, and group `0x76/8` to a ROM1/ROM2 selector. The signed RCX test shows that a payload edit invalidates its existing ECDSA signature. Neither trace yet connects the streamed body to the separate signed package reader or establishes a way to install modified firmware.

## One live empty-request observation

On 2026-10-12 UTC, a single unauthenticated HTTP/1.1 `POST /DOWN/FIRMWAREUPDATE/ROM1` with `Content-Length: 0` returned `500 Internal Server Error` with an empty body. A read-only SNMP status request succeeded just before it, timed out on the first two attempts after it, then succeeded again. One ping during the interruption failed and the next succeeded. After recovery, SNMP `sysUpTime.0` read `3600` centiseconds (36 seconds) at approximately 07:58:20 UTC; this is consistent with the network processor or SNMP agent restarting around the POST, but there is no pre-request uptime measurement and the printer already has an intermittent Wi-Fi fault. There was no firmware payload, no custom image installation, and no cake print. This is a **reproducibility lead**, not yet a confirmed denial-of-service vulnerability. Repeating a state-changing POST for confirmation would risk another interruption.

A later single POST to the same path with the 20-byte invalid marker `ET3850-INVALID-PROBE` also returned `500` with an empty body. This time the pre-request `sysUpTime.0` value was `2,506,900` centiseconds and the immediate, 5-second, and 15-second post-request values were `2,506,900`, `2,507,500`, and `2,509,000`. Uptime therefore did not reset during this bounded observation. The response does not reveal whether the marker reached the controller or whether rejection happened at the first `GetRequestID` exchange. The marker cannot parse as an RCX/`EPSONSIGN` package and no flash or print occurred. [`probe_invalid_update_marker.py`](../scripts/probe_invalid_update_marker.py) reproduces the request and uptime sampling on a user-controlled printer.

After the corrected controller trace exposed a preparation state, one bounded sequence sent unauthenticated `GET /FIRMWAREUPDATE` and, after its `200 OK` response, the same 20-byte invalid-marker POST two seconds later. The POST returned `500` and an empty body. SNMP uptime was `2,688,100` centiseconds before and immediately after the GET. SNMP then timed out immediately and five seconds after the POST; at fifteen seconds it returned `1,500` centiseconds. The printer recovered and an IPPS capability check reported idle state `3`. This establishes a network/SNMP uptime reset during the **combined sequence**, but does not identify whether the POST reached the signed reader or caused a physical printer reboot.

A single `GET /FIRMWAREUPDATE` control was then run without POST. It returned `200 OK`; SNMP uptime advanced from `5,200` to `5,800`, `6,800`, and `8,300` centiseconds at 5, 15, and 30 seconds. IPPS still reported idle state `3`. Thus the observed reset did not occur after this GET-only control. The earlier standalone invalid-marker POST also did not reset uptime. The combined sequence warrants vendor triage as a possible update-state denial-of-service, but one combined trial is insufficient to claim a reproducible vulnerability, and the user's existing Wi-Fi instability is a confounder. No further combined probe or image upload has been performed.

A 0x8c correction to the [controller CROM image](controller-crom-trace.md) resolves two earlier false negatives. The group `0x0b/0x42` event table branches to a handler rather than the wait loop. More directly for firmware POST, the 38-entry `EpsonLocalReq:` table maps `GetRequestID` to the controller's `Method:`/`URI:` parser. A literal in that parser points to `/DOWN/FIRMWAREUPDATE/`; the POST branch queues group `0x76`, subcommand `8`. The corrected [jump table](../scripts/inspect_update_event_dispatch.py) sends subcommand `8` to the ROM1/ROM2 selector. This is a coherent static first-stage controller path. It is not a live acceptance or body-to-flash proof.

The controller's separate `/FIRMWAREUPDATE` prefix callback queues group `0x76`, subcommand `6`. The corrected dispatcher routes that to Ghidra `0x45808b2c`, whose observed branches set update state `1` from state `0`, then state `5` after readiness checks in state `1`. The ROM selector requires state `5` before accepting a new ROM1/ROM2 request. This explains why a preparation GET may matter, but the live state value and the timing of these controller transitions were not measured.

On 2026-10-12 at about 18:39 UTC, the user noticed the physical ET-3850 LCD showing “Preparing for firmware update” with a loading circle and a `Cancel` option. They had not started an update from the control panel and did not know when the screen first appeared. No custom RCX had been uploaded or sent. A read-only SNMP `vi` query after the observation still returned `XB22Q5`; a read-only SNMP uptime query returned 1,180,000 centiseconds. The earlier `/FIRMWAREUPDATE` GET tests are one possible cause, but this observation does not establish what triggered the LCD state or when it began. No update endpoint was called after the screen was reported. The user selected the printer's `Cancel` option and reported that the normal screen returned. Immediately afterward, two read-only SNMP checks timed out, then a subsequent `vi` query succeeded and again returned `XB22Q5`. The short timeout may reflect Wi-Fi reconnection or the existing intermittent fault and does not establish a reboot. This is live evidence of a cancellable update-preparation state, not of image acceptance or flashing.

The route names match a [2016 researcher advisory about a WF-2540](https://lists.openwall.net/bugtraq/2016/09/26/2), which used `GET /FIRMWAREUPDATE` followed by `POST /DOWN/FIRMWAREUPDATE/ROM1`. That advisory tested a different printer and predates this signed XB20 package. Its unsigned-firmware conclusion must not be transferred to the ET-3850.

Next offline trace: identify the controller's ROM callback list and body receiver, then determine where the relayed bytes are authenticated. No new ET-3850 vulnerability or working network flash has been demonstrated.
