# Controller package index: isolated memory-safety reproduction

The decoded XB22Q5 controller image has a package-header parser at `0x457779e0`. For an `EPSON IPLJ6XB` record, it reads the second descriptor's 16-bit ID at header offset `0x38`, reduces it to one byte, scans **37** existing entries for a duplicate, and then uses the ID as an index into two writable tables. The duplicate scan is not a range check. The reader at `0x45778404` initializes exactly 37 first-table entries and invokes this parser after reading a 4096-byte package header. Other readers of the same table, such as `0x45728a94` and `0x45728dc4`, explicitly limit IDs to `< 0x25`.

The first table begins at `0x45c65a88` with 20-byte entries; the second begins at `0x45d65d6c` with 24-byte entries. In [isolated ARM emulation](../scripts/emulate_controller_header_index.py), the actual parser instructions return success and write to `0x45c65d6c` and `0x45d660e4` for ID `0x25`, the first value past the 37-entry range. ID `0xfe` writes farther past both ranges. Controls `0`, `3`, and `0x24` write within the 37 entries. ID `0xff` is rejected because unused entries have the `0xff` sentinel, which the duplicate scan matches. The emulation uses the unmodified official first header, changing only its ID for each case. It runs the complete parser and its compare routine without stubbing either function, and it never contacts the printer.

The second table ends **exactly where the copied ECDSA public key begins**: `0x45d65d6c + 37 × 24 = 0x45d660e4`. The parser's key-copy destination literal at `0x45778f08` also resolves to `0x45d660e4`. The signed-header parser at `0x45778e40` first copies the trusted 64-byte key from `0x4fb26800` into that buffer; later, the ID `0x25` IPL-header parse overwrites its first 24 bytes. The first 20 bytes come from header fields, while the following four bytes are a parser-generated pointer to the header buffer. An ID `0x26` record would land at the next 24-byte slice, and ID `0x27` would overlap the final key bytes and the start of the signature buffer. This is a concrete **key-buffer corruption path**, but it does not yet give us a valid key pair: pointer bytes in the overwritten buffer are not freely chosen, and no successful ECDSA check with a substituted key has been demonstrated.

The verifier imports both 32-byte key coordinates into elliptic-curve state through `0x45768d04` and `0x45760884`. The latter calls an additional key-check routine at `0x4576064c` before reporting success. Static analysis does not identify a malformed-point shortcut; overwriting arbitrary key bytes should not be assumed to pass verification.

The first table's ID `0x25` write lands at `0x45c65d6c`, which a separate read routine uses as a file-staging buffer. That explains where its out-of-range write goes in this image; it does not establish that a live stream can continue safely after corruption.

The RCX's ECDSA signature covers that descriptor. A one-byte change from ID `0` to `0x25` makes the [offline signature verifier](../scripts/verify_rcx_signature.py) report an invalid signature. However, `0x45778404` calls the signed-stream reader at `0x45778264` for just the first 4096 payload bytes, then calls `0x457779e0` on that header. The signed-stream routine checks ECDSA only when its declared payload byte counter reaches zero. The official package declares 40,603,648 payload bytes, so this first header is parsed **before** that routine can finish verification. This establishes a preverification out-of-range table write on this decoded code path, subject to the route actually using it.

The same signed-stream routine sets state `2` after a valid signature and still services later reads without adding them to the hash. The package reader can attempt another header after the signed content. This is a possible unsigned-append angle, **not** an established signature bypass: the surrounding transport may enforce total length, the original three sections may terminate the reader, and no accepted appended package has been demonstrated.

## Reproduction and limits

Run `python scripts/emulate_controller_header_index.py path/to/xb22q5-controller-0.bin path/to/FWCJ61TL.rcx` with Python Unicorn installed. The script checks both input hashes. It prints in-range and out-of-range controls and asserts the `0x25` result. Proprietary firmware and modified RCX bytes are not included here.

This is an **offline memory-safety finding in the decoded image**, not yet a confirmed ET-3850 network vulnerability. The test printer's read-only status reports `05.15.XB22Q5`, matching the analyzed release, but we have not linked a live LAN request to `0x45778404`, proved the physical controller's runtime memory layout, shown a device crash, or made a substituted key pass the signature check. The out-of-range write itself is not a safe way to test or install the Wi-Fi modification on a printer with no established recovery route.
