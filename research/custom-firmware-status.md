# Custom firmware route: current evidence

The intended modification is to keep the Realtek Wi-Fi device awake by changing `rtw_power_mgnt=1 rtw_enusbss=1` to `rtw_power_mgnt=0 rtw_enusbss=0` in the ET-3850 network application. This is a candidate, not a diagnosed cause of the user's Wi-Fi failures. The device's active USB Wi-Fi product ID is still unknown.

The XB22Q5 `nwsoc` executable has five loader command strings with those arguments: one for `8723du.ko` and four for `8821cu.ko`. Direct listings of both original SquashFS images contain `8723du.ko`, its firmware blob, and its driver data, but no `8821cu.ko`. That strongly suggests the 8723DU path is the active one in this package; the physical printer's USB product ID has not been read. [`patch_wifi_power_all.py`](../scripts/patch_wifi_power_all.py) changes all five command strings in an offline copy. On the extracted binary with SHA-256 `70728f452c5358c4ef04ec39354c4656c42fa6e662af675ce88d161f05949ac0`, it changes only ten digit bytes, preserves the 6,958,588-byte length, and produces SHA-256 `67a8da3124b49d1d63e8b0378ac59ec79405eab75a1a0eee3144bb1b7aacbbf2`. The script rejects other input builds and unexpected command counts.

The extracted executable starts in a QEMU rehost. A synthetic D4 `EPSON-INFORMATION` reply now lets both the original and patched `nwsoc` binaries complete printer-interface, network-interface, and WLAN-library initialization in an [offline rehost](application-rehost.md). The model does not provide USB-detector events or valid later D4 events, so it does not execute the Realtek loader command or prove the Wi-Fi fix.

An additional offline-only WebApp shim now opens HTTP listeners on ports 80 and 443 in an isolated QEMU network namespace. `GET /FIRMWAREUPDATE` returned 403; two empty update-path POSTs produced invalid status `0` responses because the internal peer is still synthetic. This confirms that the rehost can exercise route registration, not that it can emulate firmware acceptance or that the physical printer would accept the modified RCX. The WebApp shim is separate from the Wi-Fi candidate.

With an explicitly fabricated `GetRequestID` controller success reply, the generic `/DOWN/` handler forwarded a 19-byte marker body through its D4 send path in QEMU. The first run returned HTTP 500 at a later controller exchange. Fabricating a second `HR:200` stream reply made the same isolated POST return HTTP 200. This completes a Linux-side transport trace under invented controller responses; it does **not** show the real controller approving the request, accepting the modified RCX, flashing it, or fixing Wi-Fi.

An offline **RCX candidate** now contains the changed executable. The second SquashFS was rebuilt with xz compression and the original 131072-byte block size; its 2,630,514 used bytes fit within the original 2,630,538-byte slot. Re-extracting `nwsoc` from that image gives the expected patched SHA-256. [`repack_wifi_candidate.sh`](../scripts/repack_wifi_candidate.sh) reproduces the filesystem step with `unsquashfs` and `mksquashfs`. [`build_self_signed_control.py`](../scripts/build_self_signed_control.py) replaces that image in an XB22Q5 RCX, changes both embedded public-key copies, and signs the payload with an ephemeral P-256 key. The candidate retains the original RCX length. Its signature verifies against its embedded key, and its two IPL key copies agree. The generated RCX remains in local scratch space and has **not** been sent to the printer.

A second, combined offline candidate also replaces `wlan_enable_suspend.sh`, changing USB `power/control` from `auto` to `on` and Realtek `auto_suspend_block` from `0` to `1`. The repack script now accepts this optional fourth input. The combined SquashFS uses 2,630,518 bytes, leaving 20 bytes within the original slot. Re-extraction from the same-length RCX matched the patched `nwsoc` SHA-256 `67a8da3124b49d1d63e8b0378ac59ec79405eab75a1a0eee3144bb1b7aacbbf2` and patched suspend-script SHA-256 `cd69813b0b73f57582f021cb208a842900ecd47b07bda5b29e6d2f8fd032778e`. The combined RCX's embedded-key signature verifies, while the key in the currently running XB22Q5 IPL rejects it offline. This candidate has **not** been sent to the printer and does not prove a Wi-Fi fix.

The custom installation path remains the key problem. The RCX payload is signed with ECDSA P-256. A one-byte payload change makes the existing signature fail the offline verification check. The printer's own verifier has not been identified. The [network update route trace](network-update-route-trace.md) confirms built-in POST callbacks for `/DOWN/FIRMWAREUPDATE` and traces a parsed request into an internal transport channel, but neither accepted RCX upload nor device-side signature behavior has been demonstrated. The exposed `/FIRMWAREUPDATE` GET handler prepares a stateful controller update. The extracted boot sequence can execute a writable `/opt/nwsoc_data/ExtBoot` file, but no authenticated network operation has been shown to write that path. These are precise research targets rather than an installation recipe.

The offline self-signed candidate does **not** show that the printer accepts self-signed images. It shows that the candidate's embedded signature and key copies can be made internally consistent. A check against the **current** XB22Q5 IPL key rejects the candidate, while accepting the unmodified RCX. The decoded [controller package path](controller-crom-trace.md#controller-side-epsonsign-gate) now supplies a second, more specific reason: its `EPSONSIGNXB20d` parser reads its public key from `0x4fb26800`, which the extracted first IPL's startup descriptor fills from the original boot-image key. This path hashes the payload and calls P-256 signature verification before reporting package success. Replacing keys inside the incoming RCX does not alter that running key. The link between the network POST and this package path, any earlier immutable root check, and the live device's exact RAM state remain unproven.

The [first IPL boot-image trace](updater-signature.md#first-ipl-boot-image-findings) located two copies of the RCX public key, a startup copy descriptor that places one copy at `0x46308000`, and code that parses `EPSONSIGN` headers and reads its key from that address. This narrows the signature investigation to the boot-image validation path. It still leaves the acceptance decision and the authentication of the boot image unresolved.

The [secondary controller program-update image](secondary-update-mode.md) contains a real lower-level ROM programmer. It accepts memory buffers and checks byte sums after flash operations. A command-state chain now reaches a dispatcher for that programmer; its local status helpers return constants rather than checking an ECDSA signature. The command state's producer, any earlier authentication, and a network path to it remain unknown. This is an alternative route to investigate, not an unlocked installer. The separate `EPSONSIGN` verifier wrapper accepts only a cryptographic result of exactly `1`; it does not confuse an error with success.

The two available official RCX releases use the same P-256 public key but have different ECDSA `r` values. They do not show the exact repeated-nonce failure that would expose a private signing key from this pair. A self-signed image still fails against the key copied into the current IPL's verifier state.

An [isolated controller-package parser finding](controller-package-index-overflow.md) now offers a more concrete alternative to forging Epson's private key. The XB22Q5 parser accepts a header descriptor ID beyond its 37-entry table and writes past two tables. The second table ends at the very buffer that receives the trusted ECDSA public key, so ID `0x25` overwrites the key's first 24 bytes. The signed-stream reader calls that parser after the first 4096 payload bytes, before its full-payload ECDSA check can complete. A one-byte changed RCX fails its signature offline, yet the isolated parser still performs the out-of-range writes. The parser forces four pointer bytes into each 24-byte overwritten slice, so a usable replacement P-256 key has not been constructed. The network route to this exact parser and live impact remain unproved; this finding is not an installation method.

Before a physical custom flash or cake print, the remaining work is to prove that the network route accepts the RCX, determine the authentication that precedes the mapped boot-image signature check, and obtain a recoverable test path. A working QEMU application rehost could validate the candidate's driver command without touching the device. With no USB connection available, a failed flash might leave no demonstrated recovery method.

The live ET-3850 advertises `image/jpeg` and `Print-Job` over `ipps://PRINTER_IP:631/ipp/print`. A read-only capability query succeeded with the printer idle. [`create_cake_page.py`](../scripts/create_cake_page.py) prepares a letter-size JPEG and [`print_cake_ipps.py`](../scripts/print_cake_ipps.py) has a default read-only mode; its `--send` path has not been used. These prepare the requested physical cake print for after a verified custom change.
