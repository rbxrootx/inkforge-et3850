# Custom firmware route: current evidence

The intended modification is to keep the Realtek Wi-Fi device awake by changing `rtw_power_mgnt=1 rtw_enusbss=1` to `rtw_power_mgnt=0 rtw_enusbss=0` in the ET-3850 network application. This is a candidate, not a diagnosed cause of the user's Wi-Fi failures. The device's active USB Wi-Fi product ID is still unknown.

The XB22Q5 `nwsoc` executable has five loader command strings with those arguments: one for `8723du.ko` and four for `8821cu.ko`. Direct listings of both original SquashFS images contain `8723du.ko`, its firmware blob, and its driver data, but no `8821cu.ko`. That strongly suggests the 8723DU path is the active one in this package; the physical printer's USB product ID has not been read. [`patch_wifi_power_all.py`](../scripts/patch_wifi_power_all.py) changes all five command strings in an offline copy. On the extracted binary with SHA-256 `70728f452c5358c4ef04ec39354c4656c42fa6e662af675ce88d161f05949ac0`, it changes only ten digit bytes, preserves the 6,958,588-byte length, and produces SHA-256 `67a8da3124b49d1d63e8b0378ac59ec79405eab75a1a0eee3144bb1b7aacbbf2`. The script rejects other input builds and unexpected command counts.

This output is an ARM executable, not an installable printer package. It has not been sent to the printer. The extracted executable starts in a QEMU rehost but stops at an unimplemented EPIDC/D4 controller handshake before it reaches Wi-Fi initialization, so its effect on the driver has not been dynamically observed.

The custom installation path remains the key problem. The RCX payload is signed with ECDSA P-256. A one-byte payload change makes the existing signature fail the offline verification check. The printer's own verifier and any writable network route have not been identified. The exposed `/FIRMWAREUPDATE` handler prepares a stateful controller update and is not a demonstrated arbitrary-file upload. The extracted boot sequence can execute a writable `/opt/nwsoc_data/ExtBoot` file, but no authenticated network operation has been shown to write that path. These are precise research targets rather than an installation recipe.

Before a physical custom flash or cake print, the remaining work is to identify a network write/update transport for this model, determine its authorization and signature checks, and obtain a recoverable test path. A working QEMU application rehost could validate the candidate's driver command without touching the device.
