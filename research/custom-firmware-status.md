# Custom firmware route: current evidence

The intended modification is to keep the Realtek Wi-Fi device awake by changing `rtw_power_mgnt=1 rtw_enusbss=1` to `rtw_power_mgnt=0 rtw_enusbss=0` in the ET-3850 network application. This is a candidate, not a diagnosed cause of the user's Wi-Fi failures. The device's active USB Wi-Fi product ID is still unknown.

The XB22Q5 `nwsoc` executable has five loader command strings with those arguments: one for `8723du.ko` and four for `8821cu.ko`. Direct listings of both original SquashFS images contain `8723du.ko`, its firmware blob, and its driver data, but no `8821cu.ko`. That strongly suggests the 8723DU path is the active one in this package; the physical printer's USB product ID has not been read. [`patch_wifi_power_all.py`](../scripts/patch_wifi_power_all.py) changes all five command strings in an offline copy. On the extracted binary with SHA-256 `70728f452c5358c4ef04ec39354c4656c42fa6e662af675ce88d161f05949ac0`, it changes only ten digit bytes, preserves the 6,958,588-byte length, and produces SHA-256 `67a8da3124b49d1d63e8b0378ac59ec79405eab75a1a0eee3144bb1b7aacbbf2`. The script rejects other input builds and unexpected command counts.

The extracted executable starts in a QEMU rehost. A synthetic D4 `EPSON-INFORMATION` reply now lets both the original and patched `nwsoc` binaries complete printer-interface, network-interface, and WLAN-library initialization in an [offline rehost](application-rehost.md). The model does not provide USB-detector events or valid later D4 events, so it does not execute the Realtek loader command or prove the Wi-Fi fix.

An additional offline-only WebApp shim now opens HTTP listeners on ports 80 and 443 in an isolated QEMU network namespace. `GET /FIRMWAREUPDATE` returned 403; two empty update-path POSTs produced invalid status `0` responses because the internal peer is still synthetic. This confirms that the rehost can exercise route registration, not that it can emulate firmware acceptance or that the physical printer would accept the modified RCX. The WebApp shim is separate from the Wi-Fi candidate.

With an explicitly fabricated `GetRequestID` controller success reply, the generic `/DOWN/` handler forwarded a 19-byte marker body through its D4 send path in QEMU. The first run returned HTTP 500 at a later controller exchange. Fabricating a second `HR:200` stream reply made the same isolated POST return HTTP 200. A later mock used a nonzero `RequestID:1`, matching `ChID:1`, and the same request ID in the eight-byte D4 body-channel response header; it also returned 200. This completes a Linux-side transport trace under invented controller responses; it does **not** show the real controller approving the request, accepting the modified RCX, flashing it, or fixing Wi-Fi.

An offline **RCX candidate** now contains the changed executable. The second SquashFS was rebuilt with xz compression and the original 131072-byte block size; its 2,630,514 used bytes fit within the original 2,630,538-byte slot. Re-extracting `nwsoc` from that image gives the expected patched SHA-256. [`repack_wifi_candidate.sh`](../scripts/repack_wifi_candidate.sh) reproduces the filesystem step with `unsquashfs` and `mksquashfs`. [`build_self_signed_control.py`](../scripts/build_self_signed_control.py) replaces that image in an XB22Q5 RCX, changes both embedded public-key copies, and signs the payload with an ephemeral P-256 key. The candidate retains the original RCX length. Its signature verifies against its embedded key, and its two IPL key copies agree. The generated RCX remains in local scratch space and has **not** been sent to the printer.

A second, combined offline candidate also replaces `wlan_enable_suspend.sh`, changing USB `power/control` from `auto` to `on` and Realtek `auto_suspend_block` from `0` to `1`. The repack script now accepts this optional fourth input. The combined SquashFS uses 2,630,518 bytes, leaving 20 bytes within the original slot. Re-extraction from the same-length RCX matched the patched `nwsoc` SHA-256 `67a8da3124b49d1d63e8b0378ac59ec79405eab75a1a0eee3144bb1b7aacbbf2` and patched suspend-script SHA-256 `cd69813b0b73f57582f021cb208a842900ecd47b07bda5b29e6d2f8fd032778e`. The combined RCX's embedded-key signature verifies, while the key in the currently running XB22Q5 IPL rejects it offline. This candidate has **not** been sent to the printer and does not prove a Wi-Fi fix.

The custom installation path remains the key problem. The RCX payload is signed with ECDSA P-256. A one-byte payload change makes the existing signature fail the offline verification check. An extracted controller verifier uses the currently running IPL's public key, but its connection to the live network update request remains unproved. The [network update route trace](network-update-route-trace.md) confirms built-in POST callbacks for `/DOWN/FIRMWAREUPDATE` and traces a parsed request into an internal transport channel, but neither accepted RCX upload nor live device-side signature behavior has been demonstrated. The exposed `/FIRMWAREUPDATE` GET handler prepares a stateful controller update. The extracted boot sequence can execute a writable `/opt/nwsoc_data/ExtBoot` file, but no authenticated network operation has been shown to write that path. These are precise research targets rather than an installation recipe.

The offline self-signed candidate does **not** show that the printer accepts self-signed images. It shows that the candidate's embedded signature and key copies can be made internally consistent. A check against the **current** XB22Q5 IPL key rejects the candidate, while accepting the unmodified RCX. The decoded [controller package path](controller-crom-trace.md#controller-signed-package-and-trusted-key) reads its public key from `0x4fb26800`, which the extracted first IPL's startup descriptor fills from the original boot-image key. Under the original declared length, this path hashes the payload and calls P-256 verification before reporting success; replacing keys inside the incoming RCX does not alter that running key. The corrected CROM trace now resolves the POST's first-stage `GetRequestID` handler and ROM selector, but the subsequent body path to this package reader, any earlier immutable root check, and the live device's exact RAM state remain unproven.

A new [offline controller length-gate finding](controller-signature-length-bypass.md) changes that last conclusion for **this decoded reader**: a declared signed-payload length one byte larger than the three records it consumes makes the reader return success without reaching P-256 verification. A separate candidate retains the original public key and signature, replaces the Wi-Fi SquashFS, recalculates the affected record's 16-bit sum and SHA-1 digest, appends one byte, and updates the unsigned RCX sizes. Its signature is invalid against the current IPL key, but all six body sums and three record digests pass independently and the isolated ARM reader returns success with no ECDSA call. This is an offline bypass of a mapped code path, not evidence that the printer accepts the candidate over LAN, that an earlier boot or updater check allows it, or that the Wi-Fi change fixes the fault. No payload was sent to the device.

The corrected controller dispatch maps group `0x77/5` to a package receiver that calls this reader in modes `0xb` and `0x11`. The ROM1 request selector also uses branch `0xb`, and the [hash-checked chain inspector](../scripts/inspect_controller_update_chain.py) confirms the underlying branch instructions. The shared number is a useful lead, but the HTTP body channel's callback still has to be linked to group `0x77`; no network acceptance claim follows from the number alone.

The [first IPL boot-image trace](updater-signature.md#first-ipl-boot-image-findings) located two copies of the RCX public key, a startup copy descriptor that places one copy at `0x46308000`, and code that parses `EPSONSIGN` headers and reads its key from that address. This narrows the signature investigation to the boot-image validation path. It still leaves the acceptance decision and the authentication of the boot image unresolved.

The [secondary controller program-update image](secondary-update-mode.md) contains a real lower-level ROM programmer. It accepts memory buffers and checks byte sums after flash operations. A command-state chain now reaches a dispatcher for that programmer; its local status helpers return constants rather than checking an ECDSA signature. The command state's producer, any earlier authentication, and a network path to it remain unknown. This is an alternative route to investigate, not an unlocked installer. The separate `EPSONSIGN` verifier wrapper accepts only a cryptographic result of exactly `1`; it does not confuse an error with success.

Four verified RCX releases use the same P-256 public key but have distinct ECDSA `r` values. They do not show the exact repeated-nonce failure that would expose the private signing key. A self-signed image still fails against the key copied into the current IPL's verifier state.

The RCX has an [unsigned text envelope](updater-signature.md#signature-format-and-verification-paths) before its `EPSONSIGNXB20d` block. An offline same-length change to one `[B]` setting leaves the original signature valid because the payload bytes are unchanged. This may affect how the Windows updater interprets the file, but it does not authenticate our modified Wi-Fi payload or show a printer route that trusts the edited metadata. The host parser at `0x453b9d` records `Z_1`'s file offset and size; the controller package reader still validates the signed payload in its mapped path.

A fresh inventory of direct `system()`, `popen()`, and `execl()` references in the extracted `nwsoc` found shell commands for fixed maintenance actions and commands formatted with an interface name, peer address, or fixed DHCP lease-file path. The previously documented wireless-peer `ip neigh` copy remains the most concrete input-safety issue among those calls. This inventory has not identified an administrator-controlled command string or a network write to the boot hook. It is a direct-call inventory, not a proof that every possible indirect shell call has been found.

An [isolated controller-package parser finding](controller-package-index-overflow.md) is a concrete memory-safety issue, though it has **not** made our key work. The XB22Q5 parser accepts a header descriptor ID beyond its 37-entry table and writes past two tables. The second table ends at the buffer that receives the trusted ECDSA public key, so ID `0x25` overwrites the key's first 24 bytes before the full-payload ECDSA check. The next reader gate accepts only IDs `0` through `5`, however, and rejects this record after the overwrite. Isolated emulation confirms both the write and that rejection. The same reader processes only three records, closing a simple unsigned-fourth-record append. The network route to this parser and live impact remain unproved; this finding is not an installation method.

Before a physical custom flash or cake print, the remaining work is to prove that the network route accepts the RCX, determine the authentication that precedes the mapped boot-image signature check, and obtain a recoverable test path. A working QEMU application rehost could validate the candidate's driver command without touching the device. With no USB connection available, a failed flash might leave no demonstrated recovery method.

The live ET-3850 advertises `image/jpeg` and `Print-Job` over `ipps://PRINTER_IP:631/ipp/print`. A read-only capability query succeeded with the printer idle. [`create_cake_page.py`](../scripts/create_cake_page.py) prepares a letter-size JPEG and [`print_cake_ipps.py`](../scripts/print_cake_ipps.py) has a default read-only mode; its `--send` path has not been used. These prepare the requested physical cake print for after a verified custom change.
