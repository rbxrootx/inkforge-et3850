# Vulnerability tracking

**Live update (2026-10-12):** A modified image with an invalid normal ECDSA signature ran on the owner's physical ET-3850 after an owner-authorized USB update. The custom startup marker, root shell, running executable digest, and Wi-Fi driver parameters provide independent installation evidence. This establishes a firmware acceptance/security-boundary failure on the tested device. The exact live controller path and broader model/version impact remain unproven. See [live verification](live-custom-install.md). This repository is public; no vendor report has been submitted.

| Initial Web Config administrator password can be derived through SNMP when unchanged | [Epson advisory CVE-2025-35970](https://epson.ca/support/wa00965) names ET-3850. A single read-only SNMP query and one login succeeded on the test device. Serial/password are omitted here. | **Known issue, reproduced locally.** Not a new disclosure. | Grants Web Config administrator access, but no arbitrary file write or shell was identified. |
| ENUP debug authentication and raw-IP parser | [Static trace](enup-debug-channel.md) identifies IPv4 protocol 248, a 2048-bit RSA public-key challenge, authenticated Telnet and GDB triggers, NFS configuration commands, and packet-length handling leads. No protocol packet was sent during this trace. | **Protected service; no bypass or reachable memory corruption found.** | Web Config administrator login alone cannot start Telnet or write the boot hook. |
| Certificate import | Authenticated Web Config exposes `/PRESENTATIONEX/CERT/IMPORT_CHAIN` for certificate and key files. The ARM route table maps it to handler `0x226474`; that handler checks a fixed list of return paths, parses `format`, `id`, `cert0`-`cert2`, and `key`, then calls internal certificate APIs. | **Investigated; no arbitrary path or code execution demonstrated.** | A legitimate upload writes certificate material through fixed APIs; it cannot be treated as access to `/opt/nwsoc_data/ExtBoot` without proof. |
| Web Config CSRF | [Epson advisory CVE-2026-58315](https://www.epson.co.uk/en_GB/faq/KA-02075) lists ET-3850. | **Known issue; not tested locally.** | Settings modification through a victim browser is not arbitrary code execution. |
| ENPC hostname to DHCP shell | [Code trace and live probes](enpc-dhcp-lead.md) identify UDP port 3289, an authenticated configuration write path, and a later shell command using the same `IP`/`IP_HOST_NAME` key. The live ENPC device ignored the test hostname and rejected a shell expression in the domain field. Web Config `CONFIRM` reflected the expression, but after `SET`, the Basic page still showed the original name. A legal temporary name behaved the same way and was followed by a restore submission. | **Research lead; no confirmed exploit.** | Neither tested network path demonstrates shell-character storage or a boot-hook write. The device-name mode bit and Web Config apply behavior remain unresolved. |
| Web Config Basic confirmation reflection | A harmless HTML marker submitted to `NW_BASIC/CONFIRM` appeared in the response as escaped text (`&lt;`/`&gt;`), without a settings apply. | **No reflected HTML injection observed in this field.** | This probe does not establish a code-execution or boot-hook route. |
| Epson WS-Config SOAP actions | [API inventory](admin-api-inventory.md) finds `SetData`, `SetFile`, and companion actions in the extracted binary. `SetData` forwards configuration data to the controller. The `SetFile` handler does not parse a file path or body. | **Static lead; no live SOAP write or exploit.** | No arbitrary write to the Linux boot hook is shown. |
| Upload Print document route | [API inventory](admin-api-inventory.md) maps `/UploadPrint/SendDocument` to an internal relay or response builder. Its immediate callees do not expose a Linux destination path. | **Investigated offline; no live upload or vulnerability proof.** | No demonstrated write to `/opt/nwsoc_data/ExtBoot`. |
| Firmware update preparation route | The [updater trace](updater-signature.md) links uppercase `/FIRMWAREUPDATE` to an `nwsoc` handler that changes update/service state. An unauthenticated GET returned 200 once and later 500, while the printer remained reachable. | **Research lead; no sustained outage, bypass, or arbitrary upload demonstrated.** | The stateful route warrants careful offline analysis; its observed behavior does not establish a safe custom-firmware path. |
| Empty firmware-update POST and short network interruption | One unauthenticated `POST /DOWN/FIRMWAREUPDATE/ROM1` with `Content-Length: 0` returned HTTP 500. SNMP and ping briefly failed afterward, then recovered. Post-recovery `sysUpTime.0` read 36 seconds and increased on a second check. See the [route trace](network-update-route-trace.md#one-live-empty-request-observation). | **Research lead; no confirmed denial of service.** A pre-request uptime was not captured, and the Wi-Fi already drops intermittently. | The empty request did not install a custom image. Avoid repeated POST probes until the update state and recovery behavior are understood. |
| Prepared invalid update POST and network uptime reset | One unauthenticated `GET /FIRMWAREUPDATE` returned 200, then a 20-byte invalid-marker POST to `/DOWN/FIRMWAREUPDATE/ROM1` returned 500. SNMP timed out briefly and uptime reset from 2,688,100 to 1,500 centiseconds. A GET-only control kept uptime increasing for 30 seconds, and a prior standalone marker POST caused no reset. See the [route trace](network-update-route-trace.md#one-live-empty-request-observation) and [vendor triage draft](disclosure-draft-update-state-reset.md). | **Possible update-state denial-of-service lead; one combined trial, no independent repetition.** The printer recovered and the Wi-Fi is already unstable. | Shows a stateful network interruption lead, not image acceptance or a path around the signing key. |
| Wireless peer `ip neigh` address copy | The [isolated ARM reproduction](ip-neigh-buffer-lead.md) runs the extracted parser with a matching synthetic IPv6 neighbor line. Its 38-character address overwrites the guard after a 16-byte output buffer; an IPv4 control does not. | **Offline memory safety finding; not reproduced on the device.** Peer-state reachability and actual neighbor output remain unverified. | Could affect the network process in a wireless peer mode, but no crash control or firmware-install foothold has been shown. |
| Firmware update route authorization | The [route-table trace](network-update-route-trace.md) maps port 80 and 443 GET/POST handlers. With a protection flag set, port 80 returns 403 and port 443 requires Basic administrator credentials. A 2016 advisory documented similar path names on a different Epson model. | **Investigated; no bypass, accepted upload, or impact shown on ET-3850.** | A path entry does not overcome the signed RCX or prove a network installation route. |
| Generic `/DOWN/` stream | The [offline dispatcher trace](generic-down-stream.md) follows a conditional HTTP body stream into the D4 controller channel. In isolated QEMU, both paths entered the generic callback; with fabricated controller approval, a 19-byte marker reached the D4 send interface. The corrected [controller trace](controller-crom-trace.md) maps the first-stage `GetRequestID` message through ROM1 selection, a channel-1 read, and the signed package reader. | **Static controller route; no live image acceptance or vulnerability demonstrated.** | The physical controller reply, earlier validation gates, and flash result remain unresolved. |
| WebConfig command execution advisory CVE-2025-66635 | [Epson's affected-model list](https://epson.com/Support/wa00971) contains large-format and POS printers, but not ET-3850. | **Not an ET-3850 finding.** Similar code would require separate proof in this firmware. | The published advisory cannot be used as an installation foothold for this unit. |
| Boot-image embedded public key | [The IPL trace](updater-signature.md#first-ipl-boot-image-findings) follows two copies of the public key and the P-256 signature decision. An offline candidate with both copies replaced is internally consistent. | **Research lead; no device acceptance or earlier trust-chain bypass demonstrated.** | A self-signed image might still be rejected by boot ROM, update controller, or segment checks; no writable foothold is established. |
| Secondary program-update mode | [The decoded mode trace](secondary-update-mode.md) follows a command-state handler into a lower-level ROM writer that checks byte sums; the local status helpers return constants. The producer of the top-level command state is unidentified. | **Static lead; no LAN reachability, trust bypass, or device write demonstrated.** | It might matter if a network source can supply its prepared buffers, but the current trace cannot install the custom Wi-Fi image. |
| Setup restore archive filename | [Restore parser trace](setup-restore-parser.md) shows the `WRITESETUP` callback validating a CRC32 archive and then calling `open()` on each filename supplied in the archive. The backup generator's fixed file list is not checked by the restore writer. The [remote dispatch trace](remote-setup-dispatch.md) confirms that public SNMP reaches the outer `||` handler, but a zero-byte `p` probe returned `NA`. | **Static candidate; accepted archive bytes and device-side file write unproved.** | If this LAN route supplies chosen restore data and the controller accepts it, the parser could overwrite a chosen writable file. The create-capable mode could potentially write the boot hook; this has not been tested on the device. |
| Controller `SetupData:` path | [Decoded CROM trace](controller-crom-trace.md) identifies a 32-character base64 gate and an internal `SetupData:` request. Isolated ARM emulation confirms that the only traced direct producer's `IPPRes:` prefix fails this gate. | **No LAN injection or vulnerability demonstrated.** | This direct route does not provide the missing setup-restore or firmware-install foothold. Indirect producers and the internal peer still need tracing. |
| Controller group `0x76` jump-table entries 7–9 | The [corrected dispatch run](controller-event-table-memory-safety.md) maps CROM at `0x4566ff74` and selects valid handlers. The former low-address-write result came from mapping the image 0x8c too high. | **Retracted; not a vulnerability.** | Subcommand 8 now provides a static path into the ROM1/ROM2 selector. |
| Controller package-header index outside 37-entry tables | [Actual ARM emulation](controller-package-index-overflow.md) changes one descriptor ID in the first XB22Q5 IPL header. ID `0x25` writes past two tables and overlaps the copied ECDSA public-key buffer before the full payload signature check. The next reader gate rejects that ID after the write. [Vendor triage draft](disclosure-draft-package-index.md). | **Offline memory-safety and key-buffer corruption finding; LAN entry and live impact unproved.** | The post-write gate stops this route before a substituted key could validate a modified image. No safe installation path has been demonstrated. |
| Controller signed-stream length bypass | [Isolated ARM control](controller-signature-length-bypass.md) runs the decoded package reader with an unsigned declared length increased by one. The reader returns success with one byte remaining and never calls ECDSA. A modified Wi-Fi package passes record sums and SHA-1 digests while its ECDSA signature fails against the current IPL key. The static ROM1 route reaches this reader through D4 channel 1. A separate first-IPL finalizer rejects the positive byte count in an unmeasured mode; an offline four-byte patch to the *candidate* IPL skips that local error call in isolation. The controller's post-reader path hands three staged-record descriptors to a separate component whose checks are unknown. [Vendor triage draft](disclosure-draft-signature-length.md). | **Offline signature-gate bypass in the decoded reader; live acceptance, external checks, boot-ROM checks, and flash impact unproved.** | The two isolated gates can be bypassed in a candidate image, but no installation route to the physical ET-3850 is established. |
| Claimed SNMP EEPROM read community | A third-party older-model script suggested an `internal` community and a vendor EEPROM OID. On this unit, `internal` timed out; `public` gave the same eight-byte result for valid-looking and out-of-range addresses. | **No address-specific EEPROM read demonstrated.** | This lead does not supply a firmware install path. |

## Reporting threshold

Promote a research lead to a report only after reproducing it on this firmware version with a minimal proof, identifying the affected route and impact, and showing a reversible test. Do not include the printer's serial number, administrator password, Wi-Fi credentials, or proprietary firmware binaries in a public report.

Epson's [vulnerability disclosure policy](https://www.epson.eu/en_EU/faq/KA-01896) provides the reporting route for a new issue. The SNMP/default-password and CSRF issues above already have Epson advisories. The live custom-image acceptance warrants a vendor report that separates the observed installation from the unobserved controller decision path. No report has been sent.
