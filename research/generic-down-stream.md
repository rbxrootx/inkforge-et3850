# Generic `/DOWN/` body stream in XB22Q5

The XB22Q5 `nwsoc` HTTP table includes `POST /DOWN/` on ports 80 and 443, both with callback `0x1571f8`. The separate, longer `POST /DOWN/FIRMWAREUPDATE` records use callbacks `0x1553b0` and `0x1555e8`. [`inventory_http_route_table.py`](../scripts/inventory_http_route_table.py) reproduces these records from the unmodified extracted binary. The [isolated WebApp rehost](application-rehost.md) now gives a runtime observation for this activation flow: empty port-80 POSTs to both `/DOWN/` and `/DOWN/FIRMWAREUPDATE/ROM1` entered `0x1571f8` once each, while neither specific callback appeared in the filtered trace. This shows the generic prefix handling both paths in that emulated flow; it does not establish every mode on the physical printer.

The generic callback passes selector `10` to the common parser at `0x154708`. For a request parsed as body-bearing type `1`, that selector sets the body flag, reads up to `0x1000` bytes with `0x160e68`, and calls dispatcher `0x1543d0`. The reader wraps `0x13c04c`, which handles fixed-length and chunked transfer states. In the dispatcher, selector `10` requires a non-null body context and enters `0x115fdc` / `0x0f5b6c`, rather than the `0x0f8ebc` path used for selectors `5` through `7`.

At `0x0f5b6c`, a first controller exchange through `0x0f1d4c` must return status `200`. The initial exchange sends a serialized request header, including the URI and method, then parses the controller reply. The reply includes an identifier that must match one of nine configured channel entries. For a matched entry, `0x0e8130` sends the initial buffer and successive chunks through `0x42479c`, the D4/EPIC transport. The per-chunk callback is `0x1528e8`, selected from the pointer at `0x1546cc`; it calls `0x160e68` for the flagged body type. The response callback is `0x15236c`, selected from the pointer at `0x1546e0`.

The isolated rehost's D4 log now captures that first exchange in full: `EpsonLocalReq:GetRequestID`, `Method:POST`, `URI:/DOWN/` or `URI:/DOWN/FIRMWAREUPDATE/ROM1`, and `IFIndex:1`. Thus the generic HTTP callback forwards the complete request URI to the controller. The synthetic controller does not implement `GetRequestID`; it returns a placeholder channel-info reply, and the HTTP layer emits invalid status `0`. This run does not exercise the later body stream.

A separate offline build of the [controller mock](../scripts/rehost/mock_ioctl_stage.c) with `-DMOCK_GET_REQUEST_ID` supplied an **invented** `HR:200` response plus request/channel IDs. The Linux path then entered the `EPSON-NW-DOWNCONTENT1` callback for each empty POST. Its next D4 send failed in the incomplete mock and HTTP returned 500. The result confirms the two-stage control flow but does not show a transferred body, a real controller approval, or firmware validation.

With the same invented first reply (`RequestID:0`, `ChID:1`), an isolated POST to `/DOWN/FIRMWAREUPDATE/ROM1` carrying the 19-byte marker `ET3850-OFFLINE-TEST` produced an EPIDC send on the mock's channel file descriptor 10: an eight-byte length header beginning `0013`, followed by those exact 19 bytes (`4554333835302d4f46464c494e452d54455354`). The HTTP response was still 500 after a later `PNCOMIFSendData` error `6a090003`. This is dynamic evidence that the generic HTTP path **attempts to stream body bytes to the controller** when its invented initial approval is accepted. It is not evidence that the real controller would approve the URI, store the bytes, accept an RCX, or flash it. The marker was sent only to the isolated QEMU mock, never to the physical printer.

The later failure was at a second receive on D4 channel `0x10` (fd 10), after the body send. Its first receive requests an eight-byte frame header and the next requests the reply body. Adding the opt-in `MOCK_STREAM_RESULT` flag fabricates `HR:200` on this channel after the exact marker. With both this flag and `MOCK_GET_REQUEST_ID`, the isolated marker POST returned `HTTP/1.1 200 OK`. The change only proves that the Linux HTTP handler can finish the transfer when its controller peer reports success twice. Neither success reply came from the ET-3850, and this test neither installed nor validated firmware.

The fixed-target [probe script](../scripts/rehost/probe_down_marker.py) reproduced both the first-reply-only 500 result and the two-reply 200 result in separate runs. It checks for the isolated dummy interface and absence of a default route before sending any request.

The static trace and isolated marker run establish a **conditional body-transfer path** from the generic HTTP handler to the controller channel. The corrected [controller CROM trace](controller-crom-trace.md) now maps the first-stage `GetRequestID` message to the ROM1/ROM2 selector, but not the later body receiver or signed reader. A zero-byte POST to the more specific firmware path previously caused a short network interruption on the real printer; a bounded GET-plus-invalid-marker POST later coincided with an SNMP uptime reset. The generic `/DOWN/` body-transfer probe described above was made only inside the emulator. No firmware bytes have been sent to the printer.

To reproduce the decompilation, import the unmodified XB22Q5 `nwsoc` (SHA-256 `70728f452c5358c4ef04ec39354c4656c42fa6e662af675ce88d161f05949ac0`) into Ghidra and run [`ghidra_trace_down_dispatch.py`](../scripts/ghidra_trace_down_dispatch.py) as a headless post-script with an output filename. Addresses here are virtual addresses from that project. The script contains no device interaction.

Next question: identify the runtime callbacks behind ROM branch IDs `0xb`/`0xc`, connect the D4 body stream to a concrete controller reader, and determine the full validation order. Until those are established, this is a transport lead, not an installation finding.
