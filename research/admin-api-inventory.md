# ET-3850 network control and URL inventory

This inventory is based on the extracted XB22Q5 ARM application, the Windows updater bundled with Epson's recovery package, and read-only requests to a local ET-3850 running `05.15.XB22Q5`. A string in a binary is a lead, not proof that the live printer serves that URL.

| Surface | Offline evidence | Live result | Installation relevance |
| --- | --- | --- | --- |
| Web Config administrator | Authenticated menu under `/PRESENTATION/ADVANCED/` includes `NW_WIFI/TOP`, `NW_BASIC/TOP`, `SYS_ENASAVE/TOP`, and `NW_SERVICE_PRTCL/TOP`. | Login with the unchanged default administrator credential succeeded. Forms and scripts were read without storing field values. | `NW_WIFI` exposes enable/disable; `SYS_ENASAVE` exposes sleep and automatic-off timers. Neither page exposed a Wi-Fi driver power-management control or file upload. |
| Epson WS-Config SOAP | Dispatch table at `0x5baf0c` has `GetData`, `SetData`, `GetFile`, and `SetFile` actions under `http://schemas.epson.net/ws/2008/07/config/`. The `SetData` handler at `0x2029c0` parses a request and forwards a command through the printer-controller interface at `0x116994`. | Web Config reports WSD enabled. Unauthenticated GETs of `/Epson_WS_Config` and `/WSD/DEVICE` returned 404 over HTTP and HTTPS. One standards-based WS-Discovery multicast Probe received no response from the printer on this network. SOAP POST availability was not tested. | `SetData` is a genuine configuration action in the extracted program, but accepted keys, authorization, and live reachability are unresolved. No arbitrary Linux file write is established. |
| WS-Config file actions | The `GetFile` handler at `0x202158` and `SetFile` handler at `0x20229c` have nearly identical control flow. After state checks, each emits a SOAP response/fault through `0x1e7348`; neither parses a file path or body or calls a file-writing routine. | No file action sent. | The action names do not provide an identified route to `/opt/nwsoc_data/ExtBoot`. |
| Upload Print | Paired port-80/443 POST tables contain `/UploadPrint/SendDocument` with callback `0x157844`. That callback branches to the generic internal relay at `0x155180` or a response builder at `0x17111c`. The response builder's immediate callees parse request/response fields and send a response; they do not construct a Linux destination path. | No upload sent. | The route is for a print document. Static tracing found no direct write to the boot hook. |
| Generic `/DOWN/` and `/UP/` | A [hash-checked HTTP table scan](../scripts/inventory_http_route_table.py) finds paired `POST /DOWN/` callbacks at `0x1571f8` and `GET /UP/` at `0x157954`. The [generic stream trace](generic-down-stream.md) follows selector `10` through the body reader and D4 chunk sender. In isolated QEMU, the generic handler matched both `/DOWN/` and `/DOWN/FIRMWAREUPDATE/ROM1`; a 19-byte marker reached the mock D4 interface after fabricated controller approval. | No generic `/DOWN/` POST or firmware body was sent to the physical printer. Its active route mode and controller interpretation remain unknown. | A controller-facing network body path, but no proven arbitrary file write, accepted RCX, or signature bypass. |
| ENPC | UDP 3289 packet parser and authenticated configuration session documented in [ENPC/DHCP lead](enpc-dhcp-lead.md). | Read-only discovery and same-value write accepted after administrator authentication; shell-character probes did not establish storage. | Network setting write, with no code execution or file write demonstrated. |
| Epson Remote Mode over SNMP | An [independent implementation](https://github.com/Ircama/epson_print_conf/blob/main/epson_print_conf.py) encodes two-letter controller commands and payload bytes into OIDs beneath `1.3.6.1.4.1.1248.1.2.2.44.1.1.2.1`. | A read-only `st` request under `public` returned a 138-byte status value; the response content was not saved. | Confirms a controller command tunnel for status on this unit, but no identified command that supplies setup-restore data or installs custom firmware. |
| Firmware updater | `EPFWUPD.exe` includes `/firmwareupdate/checknew`, `/firmwareupdate/writenew`, `/FIRMWAREUPDATE`, `/FIRMWAREUPDATE/ADMINCHECK`, `/DOWN/FIRMWAREUPDATE/{MAIN,NET,ROM1,ROM2}`, `/update.cgi`, and `/cgi_page_down`. Its network POST and generic ECDSA P-256 verification paths are [traced here](updater-signature.md); the compiled key table omits XB20. | Prior HEADs of lowercase routes returned 404. One HTTP GET of uppercase `/FIRMWAREUPDATE` returned 200; subsequent GETs returned 500. No upload was attempted. | Generic updater paths exist, but applicable transport and signature checks for this model remain unverified. |
| Epson Device Admin | Its official guide offers a **Load from PC** firmware update option for devices supporting the feature. Epson materials list ET-3850 as Device Admin compatible, and Epson's port FAQ names TCP 443 for firmware updates. See [the Device Admin lead](device-admin-lead.md). | The software's firmware feature has not been tested against this unit. | Potential route for a local file over the network, subject to model support, format checks, signature enforcement, and recovery constraints. |
| Epson cloud | `nwsoc` contains production and staging `DSSWebService/SOAPRelayProxy.aspx` URLs. | No cloud service contacted for this research. | These are outbound service addresses, not local administrator routes. |

The recovery download is [labeled USB-only by Epson](https://epson.com/Support/Printers/All-In-Ones/ET-Series/Epson-ET-3850/s/SPT_C11CJ61201). Epson's [security overview](https://support.epson.net/security/en/index.html) describes device-side firmware signature checking for some product families; the ET-3850's exact enforcement has not been established. The current network research has **not** produced a safe custom-firmware installation path.

## Next static question

For `WS-Config SetData`, determine the accepted key namespace and controller-side authorization before any live write. It is a settings interface; the extracted handler does not show an arbitrary Linux file path parameter. For the self-built firmware path, trace the real controller's `GetRequestID` approval, body destination, and signature decision before considering a modified image.
