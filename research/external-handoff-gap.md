# ROM1 external handoff: what is missing

The [controller update-chain checker](../scripts/inspect_controller_update_chain.py) reaches two calls into code at `0x4370d47c` and `0x4370d588` after the ROM1 reader reports success. This is the next concrete boundary before claiming that a modified image can be installed. The receiving implementation is not in the controller CROM segment mapped at `0x4566ff74`.

The first IPL contains a word `0x4370d000` at raw offset `0xa37e8`, which is `0x47c` below the first external target. That raw word is inside the IPL region copied from offset `0x57004` into controller RAM at `0x43e90000`. It suggests an address relationship, but its purpose is unproved. The adjacent bytes include literals used by unrelated low-level code, so they are **not** a validated load-address table.

I checked the separately decoded CROM images for internal string pointers under a hypothetical `0x4370d000` load base. The XB22Q5 scanner image from RCX offset `0x69f112` has 77 matches at its established `0x43308000` mapping and zero at `0x4370d000`. The older XB05O7 scanner image gives the same 77-to-zero result. [`check_external_target_images.py`](../scripts/check_external_target_images.py) verifies the source hashes and reproduces these counts. Mapping the current scanner image a second time at `0x4370d000` would put the external targets at decoded offsets `0x47c` and `0x588`. In the `0x43308000` Ghidra mapping, these are **inside** functions beginning at `0x43308458` and `0x4330855c`, respectively, rather than at their entries. This makes a direct alias of that scanner image an unlikely explanation for the two external calls. The other decoded CROM images do not have a convincing concentration of string pointers at `0x4370d000` either.

The next useful evidence is either the receiving component's code or a read-only response that reveals its validation decision. A valid public key cannot yield Epson's private signing key. The existing one-byte declared-length bypass is an offline result in the mapped reader; it says nothing yet about the receiving component's checks, the first IPL's mode, or the physical printer's flash commit. The network update route and IPPS cake-print client are prepared, but no modified image has been sent or installed.

The generic HTTP `GET /UP/` handler was checked as a possible readback route. Its controller request table contains `/UP/PRINTENHANCED1` and `/UP/PRINTBASIC1`; the separate firmware prefix is `/DOWN/FIRMWAREUPDATE/`. The [hash-checked route inspector](../scripts/inspect_controller_up_routes.py) reproduces both `/UP/` entries and finds no `/UP/FIRMWAREUPDATE/` literal in the controller segment. This rules out treating the observed generic `/UP/` table as a firmware dump API. It does not prove that no other readback protocol exists.
