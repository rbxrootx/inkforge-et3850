# Local USB update route in the recovery package

Static decompilation of the locally extracted `EPFWUPD.exe` shows a local update path separate from its HTTP `/DOWN/FIRMWAREUPDATE/ROM1` path. This is **not** execution of Epson's updater and did not contact the printer.

- `0x0044470f` opens `EPSON-CTRL`, sends five-byte `fl 01 00 01`, reads a reply, and in another branch sends `gm 01 00 01`. The binary logs these as `FL` and `GM`; the actual bytes are lowercase ASCII. It compares a reply with `OK` before advancing its state.
- `0x00444b6a` opens `EPSON-DATA` after acquiring a USB mutex.
- `0x00444bd1` obtains a write-unit size, reads source firmware data, and sends it in bounded chunks through the local transport's write method. The logs mention `Data(Z_%d)` and `D4Write`.
- `0x00444a42` sends a firmware-update end command through `EPSON-CTRL` and reads its reply.

The Windows package's generic `CENUSBHost` class opens a device interface, finds one bulk IN and one bulk OUT pipe, and delegates transfers to `WinUsb_ReadPipe`/`WinUsb_WritePipe`. The attached ET-3850 has such a WinUSB interface at `MI_02`, with OUT `0x08` and IN `0x89`. The class also serves scanner-related objects, so this alone does not identify the firmware data interface.

## Live ET-3850 USBPRINT result (2026-10-12)

The attached ET-3850's USBPRINT `MI_01` device interface accepts the EJL 1284.4 enter sequence. Our own Windows Python implementation in [`usb_d4.py`](../usb_d4.py) then completed D4 Init, opened `EPSON-CTRL` socket 2, read `vi:04:05.15.XB22Q5.FY20`, and received a 137-byte `@BDC ST2` status reply. It also opened `EPSON-DATA` socket 64, reporting a 32768-byte MTU and four data transmit credits after CreditRequest. Repeated read-only sessions work after timed input draining. The official updater binary was decompiled locally; it was not executed.

The separate WinUSB `MI_02` interface also completes EJL/D4 Init and returns the same `vi`/`st` replies. A signed-stock test there received `fl:;` and `fl:01:OK;\f`, but `EPSON-DATA` socket lookup returned D4 error `0x0a` before any image byte was sent. WinUSB alone is therefore not a working DATA route in this test. Both USB interfaces still returned the same firmware version and status afterward.

Further inspection of updater routine `0x0044470f` shows its successful FL/GM branch leaves `EPSON-CTRL` open. Routine `0x00444a42` reuses that control socket for the update-end command when the socket field is set. The earlier self-built sender closed CTRL before DATA; its next revision keeps CTRL open. The first live attempt with this corrected sequence returned `fl:01:BUSY` before opening DATA. The owner then reported the panel was displaying “Preparing for firmware update,” so the corrected sequence has not yet been evaluated through a DATA transfer.

After the owner reported the home screen had returned, a read-only USB query again showed `05.15.XB22Q5.FY20`. The corrected sender then transmitted all **40,607,744 bytes** of the unchanged signed stock RCX binary over USBPRINT in about 62 seconds. The printer replied `fl:03:OK;\f` to the update-end command on the retained `EPSON-CTRL` socket. The owner subsequently reported the home screen, and a read-only USB query again returned `05.15.XB22Q5.FY20` with a 137-byte status response. This verifies a complete D4 stock-image transfer, update-end acknowledgement, and a responsive post-transfer printer. Because the sent build was identical to the installed version, the version reply alone cannot prove whether flash storage was rewritten. It is not proof that a modified image will be accepted or boot.

The sender then transmitted the **40,607,745-byte** binary payload of the local Wi-Fi/Telnet candidate over the same USBPRINT route in about 62 seconds. The printer replied `fl:03:OK;\f` at update-end. Its RCX SHA-256 is `99bae21d9ac8bbba31271dc962414ac4262e9c097d91a58b8033f5747d788249`; all three RCX record checks passed before transfer, but its embedded signature is invalid under the stock key. The acknowledgement confirms complete transport only. The printer's subsequent screen state, install acceptance, boot result, Wi-Fi behavior, and Telnet availability remain to be checked.

After that first custom transfer, the owner reported the home screen. Read-only USB `vi`/`st` still returned `05.15.XB22Q5.FY20` and a 137-byte status. A read-only IPP query confirmed `192.168.0.12` was the ET-3850, where TCP 23 presented a BusyBox-style `(none) login:` prompt. SNMP uptime began approximately 20 seconds after the transfer ended, consistent with a network processor or agent restart. The candidate password was rejected. Offline inspection then found a carriage return embedded in the first candidate's root shadow hash because the WSL repack read a Windows CRLF file without stripping `\r`; the first candidate also placed `x` in `/etc/passwd`. These findings explain a possible authentication failure and are consistent with, but do not prove, installation. The original version number was retained in the modified image, so `vi` cannot distinguish stock from custom.

A corrected second candidate has SHA-256 `8019bf8520235619d9e4dbddfff2cc08a5ec9672c8a8da2d996aa562b672749c`. Its root password hash is present without carriage returns in both `/etc/passwd` and `/etc/shadow`; the local secret matches that hash. The unchanged second SquashFS still contains the guarded Telnet watcher and Wi-Fi power-management patch. All three RCX record checks pass; normal ECDSA verification remains invalid. The USBPRINT sender transmitted all **40,607,745** binary bytes in about 63 seconds and received `fl:03:OK;\f` at update-end. Post-transfer screen, login, and Wi-Fi checks remain pending.

The owner restarted the printer because the preparation screen had no Cancel option; it returned to the same screen. Windows again enumerated the USB composite device and its printer/utility interfaces. A read-only USBPRINT `vi`/`st` check then succeeded with the original `05.15.XB22Q5.FY20` version and a 137-byte status response. This establishes that the controller was responsive after the restart, but does not show that the preparation state ended. No further `fl`/`gm` or image DATA command was sent after that observation. [Epson's ET-3850 recovery package notes](https://epson.com/Support/Printers/All-In-Ones/ET-Series/Epson-ET-3850/s/SPT_C11CJ61201) say an update can take up to 15 minutes and warn against interrupting an update in progress; its [status-message guide](https://files.support.epson.com/docid/cpd6/cpd61537/source/troubleshooting/reference/et3830_3850_l6270/problem_message_status_et3850u.html) distinguishes a displayed recovery-mode error from an ordinary update screen.

The local updater's OpenChannel constant at `0x66c398` requests four `0xffff` fields. Its revision-0x10 CreditRequest constant at `0x66c49c` is a 13-byte D4 frame whose payload is command `04`, the socket pair, `fffe`, and `ffff`. These bytes now drive the self-built transport. The updater's local send routine derives a 32762-byte data unit from the observed MTU.

[`usb_update.py`](../usb_update.py) checks exact pinned SHA-256 hashes, the RCX size and three record checks, and the current device version before live transmission. It sends `fl(1)` and `gm(1)` over `EPSON-CTRL`; the printer replied `fl:;` and `fl:01:OK;\f`. It then opened `EPSON-DATA` and streamed the **unchanged, signed XB22Q5** binary payload. Several controlled attempts stopped before the full 40,607,744 bytes were sent:

| Data frame size and channel fields | Last completed byte count | Failure |
| --- | ---: | --- |
| 4090 payload, zero trailing OpenChannel fields | at least 23,071,690 | transmit credit/write failure |
| 32762 payload, zero trailing OpenChannel fields | 7,797,356 | USBPRINT write error 5 |
| 32762 payload, full OpenChannel fields | 18,772,626 | USBPRINT write error 5 |
| 32762 payload, full OpenChannel and six-byte CreditRequest | 1,801,910 | USBPRINT write error 5 |

Those early stop offsets varied with transfer setup and did not establish a firmware record boundary or signature rejection. The printer's USB interface temporarily disappeared and the owner observed a reboot. It subsequently returned to the main menu and again answered `XB22Q5` and `@BDC ST2`. Those attempts did not reach `gm(3)`; the later corrected stock and custom sequences did. Custom-image acceptance, a recovery method after a failed custom install, and Telnet activation remain unverified.

The original printer image and the combined Wi-Fi/Telnet candidate remain local, ignored scratch artifacts. The candidate's signature is invalid under normal verification, even though its isolated controller length-gate path returned success; the live USB result does not validate that bypass.
