# Secondary controller program-update mode

The XB22Q5 RCX contains a second decoded ARM controller image at CROM header `0x69f112`. Its 1,313,312-byte segment 0 has SHA-256 `8a6fd7facdf4534eb4c5e4f4261700fb839880f006e3e0ce19dea44f1c977c9d`. A pointer to `EPSON PRINTER` and working ARM branches resolve when the image is mapped at `0x4343f000`. Run [the hash-checked inspection](../scripts/inspect_secondary_update_mode.py) against your own decoded segment to reproduce the anchors below.

A separate [debug-console trace](scanner-debug-console.md) resolves command strings and handler pointers in these same decoded bytes at base `0x43308000`, exactly `0x137000` lower. Both local mappings have anchors. The startup copy or alias relationship between them remains unverified, so the `0x4343f000` address map below should be read as the map for the ROM-programmer trace, not a proven single load base for the entire image.

Ghidra analysis shows `0x435202d8` calls the ROM programmer at `0x43448a5c`. That programmer accepts preexisting buffer addresses, lengths, ROM identifiers, and expected 16-bit checksums as arguments. For each nonempty ROM region, it runs several flash operations, then calls `0x43448788` to sum the bytes in memory and compares the result with the supplied checksum. Afterward, a status routine at `0x434487b8` draws `Program Update Mode`, `FINISHED MAIN`, version text, and three `ROMx FIXSUM` labels. This is a genuine lower-level update routine; the labels are part of its completion display.

The image also contains a command-state chain: `0x434765f8` routes one state to `0x43476188`, whose validated-command branch calls `0x43476010`. That function copies 104 bytes starting at `0x43444bfc` into a working-memory region and sends a structured internal event through `0x4346f56c`. Farther into the same dispatcher, at `0x43444db8` and `0x43444e3c`, ARM branches target `0x435202d8`, which reaches the ROM programmer. The copied 104-byte prefix does not include those branches. This extends the path back from flash operations to an internal event, but the producer of the top-level command state remains unidentified. Ghidra has no direct caller or exact function-pointer reference to `0x434765f8` in this decoded segment.

The apparent command gate at `0x4347610c` calls two helpers. In this exact image, `0x4346f78c` returns constant `0`, and `0x4346f760` returns constant `3` after unrelated setup calls. Consequently, this particular gate's decompiled condition resolves to success; it does not perform ECDSA verification itself. This says nothing about validation by the unknown producer before the command state is delivered, or by a separate boot component.

The programmer itself does not contain the `EPSONSIGN` header parser seen in the [other controller image](controller-crom-trace.md#controller-signed-package-and-trusted-key). That does **not** mean arbitrary firmware can reach it. Its arguments already point to prepared memory buffers, and this image contains no literal `HTTP`, `TFTP`, `TCP`, `USB`, `FIRMWARE`, or `EPSONSIGN` strings. The decoded image has no direct 32-bit pointer to the other image's P-256 verifier or its RAM key address `0x4fb26800`. These are narrow static observations: callers in the IPL or another image may authenticate data before this routine runs.

This mode offers a possible alternative only if a reachable, controllable caller can supply new buffers without a preceding signature gate. No such caller has been identified on the printer's network interface. It has not been invoked on the device, and no custom firmware was installed through it.
