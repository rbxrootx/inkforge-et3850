# ARM application rehost: controller boundary

The ET-3850 network application (`nwsoc`) starts under QEMU ARM user mode in an extracted Linux root filesystem. This is an **offline** test; it has no connection to the printer and does not validate a flash or a Wi-Fi fix.

At startup, the application opens `/dev/epidc0` and issues ioctl `0x400cfe00` to open an EPIDC channel. QEMU user mode rejected that device-specific ioctl before the CUSE mock saw it. A scratch-only patch to the extracted uClibc `ioctl` entry returned success, after which `nwsoc` reached the first D4 controller message. The send operation uses ioctl `0xc018fe02`; its arguments include a buffer pointer, requested byte count, and a returned byte count at offset 8. A zero-return stub left the returned count unset and caused the `Sent too much data` error. A second scratch-only stub copied the requested count into that returned field. The application then got as far as receiving the `EPSON-INFORMATION` system-command reply.

The receive operation uses ioctl `0xc018fe03` and expects a controller packet and status. A focused offline mock now supplies a D4 frame with a synthetic `MFG:EPSON;MDL:ET-3850;` device ID followed by simple placeholder replies. The application accepts the first ID, completes printer-interface initialization, and reaches its network and WLAN-library startup phases. The mock source is in [`scripts/rehost/mock_ioctl_stage.c`](../scripts/rehost/mock_ioctl_stage.c). It intercepts the one hash-identified `nwsoc` build's `ioctl` GOT slot inside a QEMU chroot. It forwards only listed read-only queries; network-setting calls receive synthetic success without changing host interfaces. It is **not** a printer payload.

The local rehost also needs an ARM ELF interpreter registered for child shell processes. That registration was temporary and removed after each run. In the scratch root filesystem alone, `ether_dummy_load.sh` returns success because the host kernel cannot load the printer's `dummy.ko`; MAC-setting ioctl is likewise answered by the mock. These emulation shims must not be interpreted as device behavior.

On the original `nwsoc` and the five-command patched binary (SHA-256 `67a8da3124b49d1d63e8b0378ac59ec79405eab75a1a0eee3144bb1b7aacbbf2`), the rehost logs `...prIF Initialized`, `...Network I/F Initialized`, and `...WCIF(WLANLib) Initialized`. The patched binary therefore starts through those phases in this incomplete offline environment. It then stops at D4 communication initialization because placeholder controller replies lack required event headers. The USB detector is absent, the WLAN firmware version prints `----`, and the Realtek module-load command is **not** reached. The rehost does not validate that power management is disabled on real hardware or that the candidate can be installed.

The key reverse-engineered functions in the XB22Q5 `nwsoc` are `0x473f58` (open channel), `0x4740d8` (send), `0x474168` (receive), `0x423148` (system response), `0x4293ac` (device ID extraction), and `0x4260d8` (startup controller configuration). The next emulator target is a valid D4 event stream and USB-detector state; neither has been modeled yet.
