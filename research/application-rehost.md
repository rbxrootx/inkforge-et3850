# ARM application rehost: controller boundary

The ET-3850 network application (`nwsoc`) starts under QEMU ARM user mode in an extracted Linux root filesystem. This is an **offline** test; it has no connection to the printer and does not validate a flash or a Wi-Fi fix.

At startup, the application opens `/dev/epidc0` and issues ioctl `0x400cfe00` to open an EPIDC channel. QEMU user mode rejected that device-specific ioctl before the CUSE mock saw it. A scratch-only patch to the extracted uClibc `ioctl` entry returned success, after which `nwsoc` reached the first D4 controller message. The send operation uses ioctl `0xc018fe02`; its arguments include a buffer pointer, requested byte count, and a returned byte count at offset 8. A zero-return stub left the returned count unset and caused the `Sent too much data` error. A second scratch-only stub copied the requested count into that returned field. The application then got as far as receiving the `EPSON-INFORMATION` system-command reply.

The receive operation uses ioctl `0xc018fe03` and expects a controller packet and status. A focused offline mock now supplies a D4 frame with a synthetic `MFG:EPSON;MDL:ET-3850;` device ID followed by simple placeholder replies. The application accepts the first ID, completes printer-interface initialization, and reaches its network and WLAN-library startup phases. The mock source is in [`scripts/rehost/mock_ioctl_stage.c`](../scripts/rehost/mock_ioctl_stage.c). It intercepts the one hash-identified `nwsoc` build's `ioctl` GOT slot inside a QEMU chroot. It forwards only listed read-only queries; network-setting calls receive synthetic success without changing host interfaces. It is **not** a printer payload.

The local rehost also needs an ARM ELF interpreter registered for child shell processes. That registration was temporary and removed after each run. In the scratch root filesystem alone, `ether_dummy_load.sh` returns success because the host kernel cannot load the printer's `dummy.ko`; MAC-setting ioctl is likewise answered by the mock. These emulation shims must not be interpreted as device behavior.

On the original `nwsoc` and the five-command patched binary (SHA-256 `67a8da3124b49d1d63e8b0378ac59ec79405eab75a1a0eee3144bb1b7aacbbf2`), the first mock logged `...prIF Initialized`, `...Network I/F Initialized`, and `...WCIF(WLANLib) Initialized`. It then stopped at D4 communication initialization because placeholder controller replies lacked valid framing.

The revised [offline controller mock](../scripts/rehost/mock_ioctl_stage.c) models six D4 channels, numbered `0x0a` through `0x0f`, and an eight-byte message header. The first two header bytes encode the payload length in big-endian order. For ioctl `0xc018fe03`, the returned byte count is word 2, the end-of-message flag is word 3, and the ioctl result is word 5. Confusing the flag and result kept the receiver in a loop. The first request on channel `0x0a` is `EpsonLocalReq:GetChannelInfo` followed by `ESC CR LF`. The reply parser seeks `UpChannelNum:` and `DownChannelNum:` fields. Later PCIF requests are `GetMainVersion` and `GetMainYearInfo`; their parser expects a status line followed by a field line. The mock supplies **invented** values solely to advance offline startup. These values are not measurements from the printer.

With these replies, both binaries log `...D4comIF initialized`, `...PCIF is initialized`, and `...SNMP Initialized` in a QEMU ARM chroot. The mock slows empty event channels to avoid an unbounded error loop. The application does not log a later HTTP listener in the 20-second run. The USB detector remains absent, the WLAN firmware version prints `----`, and the Realtek module-load command is **not** reached. None of this validates a Wi-Fi fix, a real device flash, or route behavior.

A filtered QEMU basic-block trace narrowed the next startup stall to the call at virtual `0x00098308`, immediately after the SNMP initialization log. That call enters an RSC lookup (`FUN_00047760`) for `PRT_MARKERTECH`. To test the boundary, a **scratch copy only** replaced the four call bytes at file offset `0x00088308` (`14 bd fe eb`) with `mov r0,#1` (`01 00 a0 e3`), forcing an RSC error. This bypass is not part of the Wi-Fi candidate. It lets the main startup thread log `User FirmUpdate module Initialized`, create protocol and management tasks, log `ENPC Initialized`, and exit its startup function. Subsequent protocol tasks repeatedly report missing RSC values; a WSL socket snapshot during the run showed no listeners on ports 80, 443, or 3289. Thus the mock still cannot exercise the HTTP update routes. A real controller response or representative RSC data is needed before treating the rehost as a network-service emulator.

The mock is tied to this hash-identified `nwsoc` build's GOT address. Its ARM shared object was compiled with `clang --target=arm-linux-gnueabi -march=armv7-a -shared -fPIC -nostdlib -fuse-ld=lld -Wl,-Bsymbolic`; without `-Bsymbolic`, the interposed `ioctl` failed to bind to this local override in the tested chroot. The temporary ARM binfmt registration was removed after each run. The root filesystem and binaries remain in the local scratch workspace, not this repository.

The key reverse-engineered functions in the XB22Q5 `nwsoc` are `0x473f58` (open channel), `0x4740d8` (send), `0x474168` (receive), `0x42198c` (eight-byte D4 receive), `0x000ef990` (channel-info request), `0x000ef778` (channel-info fields), `0x000f022c` (PCIF field response), `0x423148` (system response), `0x4293ac` (device ID extraction), and `0x4260d8` (startup controller configuration). The next emulator target is representative RSC service data and valid D4 events; neither has been modeled yet.
