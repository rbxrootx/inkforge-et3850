# ARM application rehost: controller boundary

The ET-3850 network application (`nwsoc`) starts under QEMU ARM user mode in an extracted Linux root filesystem. This is an **offline** test; it has no connection to the printer and does not validate a flash or a Wi-Fi fix.

At startup, the application opens `/dev/epidc0` and issues ioctl `0x400cfe00` to open an EPIDC channel. QEMU user mode rejected that device-specific ioctl before the CUSE mock saw it. A scratch-only patch to the extracted uClibc `ioctl` entry returned success, after which `nwsoc` reached the first D4 controller message. The send operation uses ioctl `0xc018fe02`; its arguments include a buffer pointer, requested byte count, and a returned byte count at offset 8. A zero-return stub left the returned count unset and caused the `Sent too much data` error. A second scratch-only stub copied the requested count into that returned field. The application then got as far as receiving the `EPSON-INFORMATION` system-command reply.

The receive operation uses ioctl `0xc018fe03` and expects a controller packet and status. A focused offline mock now supplies a D4 frame with a synthetic `MFG:EPSON;MDL:ET-3850;` device ID followed by simple placeholder replies. The application accepts the first ID, completes printer-interface initialization, and reaches its network and WLAN-library startup phases. The mock source is in [`scripts/rehost/mock_ioctl_stage.c`](../scripts/rehost/mock_ioctl_stage.c). It intercepts the one hash-identified `nwsoc` build's `ioctl` GOT slot inside a QEMU chroot. It forwards only listed read-only queries; network-setting calls receive synthetic success without changing host interfaces. It is **not** a printer payload.

The local rehost also needs an ARM ELF interpreter registered for child shell processes. That registration was temporary and removed after each run. In the scratch root filesystem alone, `ether_dummy_load.sh` returns success because the host kernel cannot load the printer's `dummy.ko`; MAC-setting ioctl is likewise answered by the mock. These emulation shims must not be interpreted as device behavior.

On the original `nwsoc` (SHA-256 `70728f452c5358c4ef04ec39354c4656c42fa6e662af675ce88d161f05949ac0`) and the five-command patched binary (SHA-256 `67a8da3124b49d1d63e8b0378ac59ec79405eab75a1a0eee3144bb1b7aacbbf2`), the first mock logged `...prIF Initialized`, `...Network I/F Initialized`, and `...WCIF(WLANLib) Initialized`. It then stopped at D4 communication initialization because placeholder controller replies lacked valid framing.

The revised [offline controller mock](../scripts/rehost/mock_ioctl_stage.c) models six D4 channels, numbered `0x0a` through `0x0f`, and an eight-byte message header. The first two header bytes encode the payload length in big-endian order. For ioctl `0xc018fe03`, the returned byte count is word 2, the end-of-message flag is word 3, and the ioctl result is word 5. Confusing the flag and result kept the receiver in a loop. The first request on channel `0x0a` is `EpsonLocalReq:GetChannelInfo` followed by `ESC CR LF`. The reply parser seeks `UpChannelNum:` and `DownChannelNum:` fields. Later PCIF requests are `GetMainVersion` and `GetMainYearInfo`; their parser expects a status line followed by a field line. The mock supplies **invented** values solely to advance offline startup. These values are not measurements from the printer.

With these replies, both binaries independently log `...D4comIF initialized`, `...PCIF is initialized`, and `...SNMP Initialized` in a QEMU ARM chroot. The original run used a hash-checked copy of the extracted `nwsoc`; the five-command candidate was the active binary in the scratch root filesystem. A separate file named `nwsoc.patched` contains an unrelated scratch experiment and was not used as the five-command comparison. The mock slows empty event channels to avoid an unbounded error loop. The application does not log a later HTTP listener in the 20-second run. The USB detector remains absent, the WLAN firmware version prints `----`, and the Realtek module-load command is **not** reached. None of this validates a Wi-Fi fix, a real device flash, or route behavior.

A filtered QEMU basic-block trace narrowed the next startup stall to the call at virtual `0x00098308`, immediately after the SNMP initialization log. That call enters an RSC lookup (`FUN_00047760`) for `PRT_MARKERTECH`. To test the boundary, a **scratch copy only** replaced the four call bytes at file offset `0x00088308` (`14 bd fe eb`) with `mov r0,#1` (`01 00 a0 e3`), forcing an RSC error. This bypass is not part of the Wi-Fi candidate. It lets the main startup thread log `User FirmUpdate module Initialized`, create protocol and management tasks, log `ENPC Initialized`, and exit its startup function. Subsequent protocol tasks repeatedly report missing RSC values; a WSL socket snapshot during the run showed no listeners on ports 80, 443, or 3289. Thus the mock still cannot exercise the HTTP update routes. A real controller response or representative RSC data is needed before treating the rehost as a network-service emulator.

An additional isolated-network run used a dummy `eth0` with documentation address `192.0.2.2`; it reached the same management-task stage but showed no listener at the ten-second socket snapshot. The binary's management-service strings place `Initializing HTTP server...` after separate start, link-connected, and IP-initialized semaphore gates, none of which the mock presently drives. Forcing both RSC getters to return value `1` globally in another scratch copy caused network-interface initialization to fail earlier, so broad RSC substitution is not a valid emulator model. These trials did not contact the physical printer.

The console menu's `y` option is labeled as a management-service start trigger, but the inspected handler at `0x000a0ab8` only prints the current service-state flags for that input. It does not release the link or IP semaphores. Supplying `y` to the offline console did not start an HTTP listener. A valid controller event or a more precise isolated startup shim is still required.

A narrower [offline patch builder](../scripts/rehost/patch_http_gates.py) now starts from the hash-checked original binary and changes four ARM instructions in a scratch copy: it forces the unresolved `PRT_MARKERTECH` lookup to fail, then bypasses the HTTP-start, link, and IP semaphore waits at `0x9f818`, `0x9f860`, and `0x9f878`. Its output SHA-256 is `435851903b973a9a9a0d1d3b768bb9c067e84f96e2ec1e746bf382e62c5fd43c`. In an isolated WSL network namespace with dummy `eth0` at `192.0.2.2`, the QEMU process logged `Initializing HTTP server...` and `...HTTP server Initialized`. A socket snapshot 12 seconds into the run showed only the UDP/161 SNMP listener and no TCP/80 or TCP/443 listener. The patch therefore advances initialization but does not yet provide a working HTTP emulator. It is unrelated to the five-command Wi-Fi candidate and must not be installed on the printer.

Decompilation explains part of this gap: the HTTP initialization call at `0x1287b0` creates worker tasks, while the separate `0x128dd8` route-registration path can reach socket bind/listen through `0x125b04`, `0x145644`, and `0x0a72fc`. The isolated run did not show a TCP listener, so the next emulator step is to determine which configuration or controller state activates that registration path. The log line saying the server was initialized is not evidence that a route is listening.

One direct activation chain is now visible: callback `0x16dab4` launches the `0x16fc18` worker only after two readiness checks and an event whose first byte is `1`. That worker reaches the matching-path registration function `0x16de88` and sets `WEBAPP_CURRENT_ACTIVATION` after success. The current synthetic controller does not supply a corresponding event, which is a plausible reason this rehost has no WebApp TCP listener. The event's actual producer and the rest of the startup conditions still need verification.

A filtered QEMU basic-block trace tested that explanation. Calling `0x16de88` directly at startup reached `0x16deac` and returned immediately: its first call, `0x16c5b8`, needs a semaphore that the worker normally creates. A second scratch copy called the full `0x16fc18` worker, omitting its `free()` because the borrowed startup call supplies an integer instead of the worker's allocated argument. The worker successfully created its semaphores in `0x16fa4c`, then exited at `0x16fd10` because `0x11c3d4` could not obtain the configuration value from the synthetic controller. This trace identifies two separate missing prerequisites rather than a missing route-table record.

The hash-checked [WebApp rehost patch](../scripts/rehost/patch_webapp_rehost.py) adds a narrow offline success value for that one configuration call. Starting from the HTTP-gates copy above, its output SHA-256 is `f23f3e1b1aed02ec4be9d46d5ff07fe3021b600cfeb15c67b77e72d725d1a398`. In the isolated network namespace, this copy executed `0x128dd8` and opened TCP listeners on IPv4 and IPv6 ports **80 and 443**. A raw `GET /FIRMWAREUPDATE` at `192.0.2.2` returned `HTTP/1.1 403 Forbidden`, confirming that the emulated listener served that registered route. Empty `POST /DOWN/` and `POST /DOWN/FIRMWAREUPDATE/ROM1` requests each returned `HTTP/1.1 0 Unknown error` in this synthetic environment. That invalid status is a consequence of incomplete internal response modeling, not a reported response from the real printer. A subsequent filtered QEMU trace showed two entries at generic callback `0x1571f8`, one for each POST, and no entry at specific callback `0x1553b0` or `0x1555e8`. Thus the generic handler matched both POST paths in this WebApp activation flow. The probes carried zero body bytes and remained inside the isolated namespace.

The bounded D4 send log captured both controller-facing first-stage messages. They begin `EpsonLocalReq:GetRequestID`, then carry `Method:POST`, the complete original request URI (`/DOWN/` or `/DOWN/FIRMWAREUPDATE/ROM1`), and `IFIndex:1`. Field separators include ESC bytes. The HTTP generic handler therefore preserves the longer URI when forwarding to the controller; the prefix match does not truncate it. The mock currently answers this command with its placeholder channel-info reply, explaining why its resulting HTTP status cannot represent controller acceptance.

The mock also has an explicitly optional `MOCK_GET_REQUEST_ID` build flag for a second offline control-flow test. It invents `HR:200`, `RequestID:0`, and `ChID:1`; these values are **not** a captured printer reply. With that flag, both empty POSTs advanced to the `EPSON-NW-DOWNCONTENT1` D4 callback and returned HTTP 500 after `PNCOMIFSendData` reported `6a090003` and `UPnPCRExecOperation` logged `send command error`. Using invented request ID `1` first produced a `Received ID(0) != Request ID(1)` error; changing it to `0` passed that check but still failed at the next unmodeled D4 command. This confirms a second controller interaction after `GetRequestID`, not a successful body transfer or update authorization. The default mock was restored after the trial.

A further isolated test kept the invented first reply and sent the 19-byte body `ET3850-OFFLINE-TEST` to `/DOWN/FIRMWAREUPDATE/ROM1`. The mock logged an eight-byte D4 header with length `0x13`, then a 19-byte send on fd 10 matching the marker exactly. The subsequent controller exchange still failed with HTTP 500. This verifies body forwarding in the **emulated Linux path** under synthetic approval; it does not model the real controller's decision or make the Wi-Fi image installable. The default mock was rebuilt after this test.

An offline SNMP command-tunnel trial on the less-patched startup copy sent `sysDescr` and the two-letter `fl` firmware-load command only to the QEMU namespace at `192.0.2.2`. UDP/161 was bound and queued datagrams, but **neither request received a reply**. The synthetic controller therefore cannot establish whether `fl` activates another update route. No `fl` request was sent to the physical printer.

This gives a working HTTP **service** emulator for route and request tracing. It is still not a device emulator for the update controller, signature decision, Realtek driver load, or Wi-Fi behavior. The three WebApp shims and four earlier startup shims are QEMU research aids only; none are in the five-command Wi-Fi candidate or suitable for installation.

The mock is tied to this hash-identified `nwsoc` build's GOT address. Its ARM shared object was compiled with `clang --target=arm-linux-gnueabi -march=armv7-a -shared -fPIC -nostdlib -fuse-ld=lld -Wl,-Bsymbolic`; without `-Bsymbolic`, the interposed `ioctl` failed to bind to this local override in the tested chroot. The temporary ARM binfmt registration was removed after each run. The root filesystem and binaries remain in the local scratch workspace, not this repository.

The key reverse-engineered functions in the XB22Q5 `nwsoc` are `0x473f58` (open channel), `0x4740d8` (send), `0x474168` (receive), `0x42198c` (eight-byte D4 receive), `0x000ef990` (channel-info request), `0x000ef778` (channel-info fields), `0x000f022c` (PCIF field response), `0x423148` (system response), `0x4293ac` (device ID extraction), and `0x4260d8` (startup controller configuration). The next emulator target is representative RSC service data and valid D4 events; neither has been modeled yet.
