# Telnet unlock path in the extracted XB22Q5 image

The extracted second SquashFS contains `watch_telnetd_trigger.sh`. It checks once per second for `/tmp/enup_auth_success` and then runs `telnetd` if no Telnet daemon is in the process list. The extracted `nwsoc` program creates that flag only after an ENUP RSA challenge response passes. The corresponding private key was not found in the extracted image, and no alternative live trigger has been established. See [ENUP trace](enup-debug-channel.md).

The extracted first SquashFS has `telnetd` and its `/etc/passwd` and `/etc/shadow` entries show `root::...`: the root password field is empty in both files. This is an **offline image observation**; the running system could overlay or replace account data. If those entries are used at runtime, forcing the watcher to launch Telnet would expose a passwordless root login on the printer's network. A custom-image Telnet unlock should therefore set a chosen password or restrict the daemon to a controlled interface before activation. A keyed SSH service would be a better long-term shell once we have code execution and a verified installation path.

An offline combined candidate now replaces the first SquashFS root account with a generated nonempty MD5-crypt password hash, changes the second SquashFS watcher to start `telnetd` only when that hash is present, and includes the candidate Wi-Fi power change. Fresh `unsquashfs -cat` reads matched the intended password hash, watcher guard, and patched `nwsoc` digest. The password itself stays in local ignored scratch space, outside this repository. Both rebuilt filesystems fit their original RCX slots, and the combined RCX passes all three record sums and SHA-1 checks. Isolated ARM runs reached the length-gate bypass and skipped the patched first-IPL rejection branch. These are offline checks; the normal ECDSA signature is invalid.

There is no observed stock SSH daemon, successful Telnet session, ENUP authentication bypass, or device-side shell. The custom Python workbench probes TCP 22 and 23 only when given a printer address. Its experimental USB sender did not complete even an unchanged signed-image transfer: the printer dropped the interface midstream, rebooted, and returned with version `XB22Q5`. No custom bytes have been sent, and Telnet has not been enabled. See [the live USB trace](usb-update-route.md).
