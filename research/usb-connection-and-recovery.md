# USB connection and recovery boundary

On 2026-10-12 the owner connected the ET-3850 to the Windows research PC with a USB cable. Windows enumerated `VID_04B8&PID_1181` as a composite device with printing, scanning, and Epson Utility functions. Interface `MI_02` uses `WinUSB` and reports vendor class/subclass/protocol `ff:aa:01`. A read-only `WinUsb_QueryInterfaceSettings` and `WinUsb_QueryPipe` check returned two bulk endpoints: OUT `0x08` and IN `0x89`, each with a 512-byte maximum packet. [The Windows inspector](../scripts/inspect_et3850_winusb.py) reproduces this descriptor check.

Static inspection of the locally extracted `EPFWUPD.exe` shows a generic `CENUSBHost` class dynamically loading `winusb.dll` and using `WinUsb_Initialize`, `WinUsb_QueryPipe`, `WinUsb_ReadPipe`, and `WinUsb_WritePipe`. Its open routine looks for one bulk IN and one bulk OUT pipe. Its transfer methods pass caller-supplied buffers directly to those pipes. A [separate local update trace](usb-update-route.md) identifies `EPSON-CTRL` commands and an `EPSON-DATA` chunk sender in the same package. Live tests show that both MI_01 and MI_02 answer D4 control commands; only MI_01 opened `EPSON-DATA`. The generic WinUSB host is also used by scanner-related objects.

The [ET-3850 user guide](https://download4.epson.biz/sec_pubs/et-3850_series/useg/en/GUID-E83E8F59-3D8B-4EC3-86D0-7FC5B6BB1076.htm) states that recovery mode requires USB and cannot update over the network. Epson's [ET-3850 support page](https://epson.com/Support/Printers/All-In-Ones/ET-Series/Epson-ET-3850/s/SPT_C11CJ61201) lists a recovery-mode image for XB22Q5 and says to use it only when the control panel displays a recovery-mode error. These documents establish a supported USB recovery scenario, not that our self-built client can perform it or that a modified IPL will be accepted.

The cable removes the previous *absence of a physical USB connection*. Several early USBPRINT attempts sent partial unchanged signed-stock data and ended before update-end. After correcting the control-socket lifetime, the self-built sender transferred all 40,607,744 signed-stock payload bytes and received `fl:03:OK` at update-end. Post-transfer device state still needs checking. The remaining gates are a validated controller handoff and custom-image acceptance rule, plus a way to restore the stock image if a custom trial fails. No modified image has been sent, and no verified custom install or cake print has occurred.

Windows also has an `EPSON ET-3850 Series` print queue on port `USB001`, reporting Normal. [The USB cake-print script](../scripts/print_cake_usb.ps1) defaults to a read-only queue and image check; `-Send` is reserved for after a verified custom installation. This gives the final print a wired route even if Wi-Fi is still unreliable.
